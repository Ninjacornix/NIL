# NIL v0.1 semantic core and provisional lines-v0 profile

Status: implemented M1 experiment. Syntax and integer policy are not stable releases.
The semantic operations are integer constant, add, subtract, multiply, signed divide,
function call and return. This legacy line frontend supports only `i64`; the current semantic HIR also has
`Bool` and structured control-flow regions, documented in [M2](CONTROL_FLOW.md). No conversions or overloaded operators.

## Grammar

```ebnf
program     = function, { function } ;
function    = "fn", uint, { "i64" }, "->", "i64", newline,
              { instruction, newline }, "ret", uint, newline, "end" ;
instruction = "const", integer
            | ("add" | "sub" | "mul" | "div"), uint, uint
            | "call", uint, { uint } ;
uint        = "0" | nonzero_digit, { digit } ;
integer     = uint | "-", nonzero_digit, { digit } ;
```

Each directive occupies one line; `end` must also occupy its own line. ASCII spaces,
tabs, CRLF/LF, empty lines and final EOF without a newline are accepted. No comments,
aliases, infix syntax or multiple directives per line. Unsigned IDs fit `u32`;
integers fit signed 64 bits. Leading zeros, plus signs and negative zero are rejected.
Signatures use explicit parameter types and one result type. Numeric function labels
must be unique but need not be dense. Arguments have implicit local IDs starting at
zero; each instruction produces the next ID. Constants are instructions, never
ambiguous literal operands. Calls consume the rest of their line; the checker verifies
arity against the resolved signature. All functions are checked, even unused ones.

```text
fn 0 -> i64
const 20
const 22
call 1 0 1
ret 2
end
fn 1 i64 i64 -> i64
add 0 1
ret 2
end
```

Execution starts at source function `0` by default and returns `42`. The M1 CLI
allows selecting another function and supplying signed i64 arguments.

## Semantics and limits

Values are immutable. Instructions and call arguments evaluate in source order.
Addition, subtraction and multiplication trap on signed overflow. Division truncates
toward zero; zero divisors and `MIN / -1` trap. Debug and release agree. Calls have no
side effects; recursion is valid but does not terminate without control flow.

Prototype limits: reject source larger than 1 MiB; default to 100,000
instruction/return steps and 256 simultaneous frames, including the entry frame.
Limits are execution policy, not language semantics. Budget exhaustion is a diagnostic.
The reference evaluator uses an explicit frame stack; the native backend preserves
the same budgets with an explicit context and bounded native calls.

## Diagnostics

Diagnostics preserve a code, phase, optional half-open UTF-8 byte span, message, and
optional expected/actual fields. Compact rendering is `CODE @start..end message`.
Codes: E001 syntax, E002 unsupported type, E003 duplicate function, E004 unknown
function, E005 invalid value, E006 arity, E007 invalid HIR/type, E008 resource limit,
E009 arithmetic trap. E010 handles CLI usage/I/O; E011 reports backend/toolchain errors. These codes are provisional.
Machine JSON and structural repair protocols are deferred; Rust consumers can
inspect diagnostic fields. First-error reporting is deterministic.

## CLI and API

`nil --profile lines-v0 check FILE` parses, checks and validates all functions without running them.
`nil --profile lines-v0 hir FILE` displays a deterministic debugging projection (not serialized source).
`nil --profile lines-v0 run FILE [FUNCTION_ID [I64_ARGUMENT...]]` compiles with LLVM
and executes natively with default resource limits. The default source profile is
expr-v0. See [native builds](NATIVE_LLVM.md) for Clang requirements and `build` usage.
Success exits 0; source/runtime/I/O errors exit 1; CLI usage errors exit 2. Program
results go to stdout and diagnostics to stderr. CLI argument numbers use Rust integer
parsing; source literals follow the stricter canonical spelling grammar above.

Library callers use `nil_compiler::compile`, select a source label with `function`,
and pass the validated HIR to `nil_llvm::build`/`run` for native execution or
`evaluator::execute` for the reference oracle. Execution limits are configurable
through the library's `Limits` struct. Alternate frontends may construct `nil_hir::Program`
and use `nil_hir::validate` directly, without the lines-v0 AST.
