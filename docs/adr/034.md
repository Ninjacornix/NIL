# ADR 034 — Statically specialized higher-order functions

## Context

ADR 026 requires proofs derived from visible bodies, not promises of purity.
The standard library needs function arguments before comparator sort or general
map/reduce can migrate. Runtime function storage would change the type and arena
model. This round adds an abstraction, not an intrinsic (35 → 35).

## Decision

### Model and limits

An expr-v5 function parameter may have a **first-order function signature**. All
such arguments resolve statically to existing local or module-exported functions.
Before typed HIR lowering, specialize the syntactic template for each distinct
ordered callback-label tuple; remove its static parameters and references and emit
only ordinary direct calls. HIR types/operations remain unchanged: no function
values, closures, indirect calls or dynamic dispatch. Runtime arguments preserve
left-to-right order; a static argument has no evaluation or effect.

Callback signatures contain existing value types only, with explicit result types;
callbacks accepting callbacks are deferred. Captured state is an ordinary explicit
typed argument, not an implicit capture. Template recursion with the same callback
configuration uses the already reserved specialization, preserving runtime depth
checks. Switching among finite known configurations is permitted. Bound all
specializations to 1,024 globally, 256 per template, 4,096 emitted functions and
1,048,576 cloned AST instructions (including nested regions); exceeding any bound
is E008 at the requesting call. No expanding/polymorphic type recursion exists.
Uninstantiated templates have no executable entry; bodies are parsed, but their
value-type checking happens when instantiated. Unknown explicit references are
checked even in unused templates. Wrong arity is E006; callback/value/signature
mismatch or attempted function escape is E007; unknown function is E004; unknown
callback parameter E005; malformed syntax E001 with byte span.

### Measured surface

`benchmarks/hof-study/forecast.py` uses tiktoken 0.12.0. These costs are identical
for cl100k and o200k; whole example comparisons include declarations:

| Candidate | Tokens | Choice |
|---|---:|---|
| `fn(i):i` | 4 | reject extra token |
| `(i):i` | 3 | reject confusing signature nesting |
| `[i:i]` | 3 | callback type |
| `&b` / `fn(b)` / `ref(b)` | 2 / 3 / 3 | `&b` local reference |
| `^b(a)` / `apply(b,a)` | 4 / 4 | caret static parameter call |
| `&!plugin(1,0)` | 8 | module export reference, existing qualification |
| named complete example / hypothetical anonymous example | 20 / 21 | no anonymous functions |

`([i:i],i)=^a(b)` accepts a callback in position a and a runtime i64 in b.
`=b(&c,20)` passes local c. `^a` forwards a statically bound callback; `&a`
always means local function a; `a(...)` always means the existing local call.
This resolves parameter/function ambiguity without changing old meanings. Static
parameters remain lexically available inside loop/each regions through `^name`,
whose name denotes the enclosing function's signature position, not loop state.
Value state still uses the existing positional letters. `[:s]` is a zero-argument
callback returning bytes. No callback can occupy record/sequence/loop state or be
returned as a value. Both arms are statically checked/specialized; only the selected
arm executes. Specialization never performs host effects or executes user bodies.

### Proofs and linking

Ordinary specialization copies flow into the existing validated HIR and whole-
program allocation, borrowing, alias/escape, reuse, effect and trap analysis.
A callback's facts derive from its actual body, including recursive fixed-point
analysis; no source annotation grants a proof. An effectful instantiation cannot
contaminate a separate pure instantiation. Existing conservative cases stay so.
`each`, `sort` and bulk equality retain their contracts; direct-call specialization
allows their existing analyses, not a new assertion of purity or matching.

Extend the same source module linker: relocate local references with local calls,
resolve export references, then specialize the fully linked module. A module can
export a template and receive a caller-local callback. Transitive import visibility,
cycles, type identity and E024 loader failures are unchanged. `nil-plugin 1`
rejects function-typed provider parameters in this round; source modules are the
supported HOF library boundary. No foreign loading or runtime addresses.

### Task selection and forecast (fixed before implementation)

Attempt **ex_accumulate** without changing frozen inputs, oracle or goldens. Its
five selected canonical fixtures include numeric square, ASCII upcase, reverse,
and a nested accumulate with captured prefix. Explicit state arguments and finite
record-buffer nesting should express them; forecast one newly supported task if
its JSON/pseudocode adapter can be authored and verified. It currently has no NIL
or baseline solutions, so a before/after density saving is **undefined**, not a
forecasted reduction. Do not fake a callback by dispatching fixture outputs.

**ex_reactive is absent from the frozen corpus**; classify it as a prospective
mutable subscriber/callback registration abstraction, not statically known call
arguments alone. Existing ex_hangman explicitly requires reactive integration:
static specialization does not supply dynamically changing subscriber state, so
forecast no new support; retain its frozen contract. No other task rewrites.

## Alternatives

Defunctionalization (tag + switch) needs runtime function storage and conservative
join summaries, changing proof boundaries without a demonstrated need. Function
pointers hide target bodies and permit indirect recursion/escape; preserving arena
and effect proofs requires a different abstraction goal. Capturing closures need
lifetime/layout semantics; explicit ordinary state suffices for this subset.
Anonymous literals cost one extra token in the measured smallest complete example
and introduce scope/capture machinery, so are excluded. No arbitrary annotations.

## Consequences

Static HOFs have ordinary direct-call costs and can cross source modules. Code
size and compile time can increase, bounded explicitly; callbacks cannot vary at
runtime. A real map control, non-inlinable callback control and comparator-sort
baseline must measure costs and vectorization, not infer performance from design.
Earlier profiles/default syntax and all verified program meanings stay unchanged.
Part B is deferred unless every Part A validation gate passes.

## Status

Accepted prototype plan, committed before compiler implementation. Nothing pushed.
