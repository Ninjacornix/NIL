# ADR 013 — expr-v3 machine-integer semantics

## Context

The user requests a new compact expression profile capable of C++-class native
execution. The measured v2/C++ comparison shows that checked C++ performs close
to v2, while ordinary C++ permits more optimization. Checked overflow and exact
per-instruction fuel accounting are explicit earlier prototype policies, not
requirements of the original research. Raw tokens and LLM repair cost remain
separate metrics. No existing research establishes a final arithmetic policy.

## Decision

Implement an opt-in expr-v3 experiment, with exactly v2's surface grammar and
fixed signed i64 signatures. Attach an explicit arithmetic mode to semantic HIR:
v3 add/sub/mul wrap modulo 2^64; signed division truncates toward zero, traps on
zero, and returns MIN for MIN/-1. Comparisons remain signed. This is deterministic
machine arithmetic, not C++'s undefined signed overflow. Earlier profiles retain
checked arithmetic; programs cannot silently mix arithmetic modes.

Resource counting is tooling instrumentation, not v3 language semantics. Native
v3 builds omit fuel/depth accounting by default. A bounded mode remains available
for validation/repair; the reference evaluator remains bounded. Production loops
and recursion may run indefinitely or exhaust the host stack. Parser/type/source
limits remain enforced. Keep semantics independent of optimization level.

Use plain LLVM integer operations without nsw/nuw promises. LLVM may optimize
loops when wrapping behavior is preserved. Never mark unchecked signed overflow
undefined merely to win benchmarks. If wrapping code does not reach C++-class
performance on the existing corpus, investigate lowering/optimization and record
remaining differences rather than claiming success.

## Alternatives

Removing only fuel retains overflow side effects and may still block loop folding.
Undefined overflow matches ordinary C++ but weakens deterministic language rules.
Adding source contracts/types is promising later but increases grammar/token cost
before measurement. Changing punctuation adds no optimizer information here.

## Consequences

No additional generated source tokens: the out-of-band profile selects semantics.
The same bytes intentionally have different overflow behavior in v2/v3, so tooling
must retain the profile and HIR mode. Explicit wrapping can conceal generated
arithmetic mistakes; model-generation/TCR experiments must evaluate that tradeoff.
Native timing/token measurements and signed-boundary/differential tests are required
before claiming this experiment meets its performance objective. v3 is not adopted
as the default and the full type-system/IR milestones remain open.

## Status

Accepted as a user-requested experiment; performance hypothesis under evaluation.

## Evidence

[Recorded regular/stress/token experiments](../../benchmarks/paired/results/2026-09-30/EXPR_V3.md)
meet the current-core parity target. Removing counters alone did not close the sum-loop
gap; wrapping arithmetic allowed LLVM formula replacement. A division branch-layout
hint preserves exceptional-case behavior and closes the measured GCD layout gap.
The [LLVM sdiv contract](https://llvm.org/docs/LangRef.html#sdiv-instruction) requires
zero and signed-overflow cases to be handled before division; v3 does not issue an
unchecked MIN/-1 division. This experiment does not settle model-generation TCR.
