# ADR 054 — The intraprocedural live-root-retention copy

## Status

Proposed, 2026-10-14. Diagnosis **incomplete**; no compiler code was written
under this ADR. Append-only.

## What is established

`--explain-copies`, run correctly, reports the copy with site, reason and
retaining root on both programs:

```text
redundant-connection, largest fixture
  kind replace, 800000 bytes, span [320,335] = "[g(a,b):g(a,c)]"
  retaining_use [220,235] = "g(b,a[2+c*2+1])"
  reason live-root-retention

course-schedule v1, largest fixture
  kind replace, 800000 bytes, span [710,727] = "[c:b.counts[c]-1]"
  kind replace, 800000 bytes, span [750,760] = "[b.tail:c]"
  retaining_use [783,784] = "?"    (a ternary)
```

In `redundant-connection` the loop carries four slots — input, parent buffer,
index, answer — and in one step the parent slot's next value is `f(b,…)`, the
union, which updates in place, while the answer slot's next value evaluates
`g(b,…)` twice against the same buffer. That shape is consistent with the
reported retaining root.

## What is NOT established

**The hypothesis that a sibling state expression's read creates the second root
is unconfirmed.** Three minimal reproductions were written and **none copied**:

| Probe | Shape | Copy hints |
|---|---|---:|
| no sibling | loop slot updated in a callee, nothing else reads it | **0** |
| element sibling | sibling slot reads `a[b]` in the same step | **0** |
| call sibling | sibling slot calls a function taking the whole buffer | **0** |

So the small cases that look like `redundant-connection` do **not** reproduce
the copy, which means the trigger involves something the probes lack. The
remaining candidates, in the order worth testing:

1. The update's own **index operands** are calls that take the same buffer —
   `a[g(a,b):g(a,c)]` roots `a` twice inside the update expression itself. This
   now looks more likely than the sibling-read story, because the reported
   update span *is* that expression.
2. The buffer is a **row of a nested structure** (`b.counts`, `b.tail` in
   `course-schedule`), so the parent record holds a child edge the probes have
   no analogue for.
3. Scale: the probes use 4,096 elements and 64 iterations; the real cases use
   20,000-element buffers and tens of thousands of iterations, and the
   reuse proof may be capacity- or collection-dependent.

**No mechanism is proposed here**, because proposing one before a minimal
reproduction exists is how the last three rounds' mis-rankings happened.

## Forecast

The goal text asked for a forecast of `course-schedule` and
`redundant-connection` reaching ≤3× C++. I am not recording that forecast,
because the diagnosis does not yet support it. What I will record:

* If candidate 1 is the cause, the fix is local — evaluate index operands to
  values before the update so the buffer is not rooted by a pending call — and
  `redundant-connection` should fall from 137.5× to within a small factor of
  C++, since 99% of its time is the copy.
* If candidate 2 is the cause, this is the child-edge work ADR 051 described
  and it is **not** intraprocedural after all, which would partly reinstate
  that ADR's framing and make the round-33 report's "cheaper than believed"
  claim wrong.
* Candidate 3 would mean there is no semantic obstacle at all, only a
  conservative proof, which is the best case and the least likely.

## Obligations when the work is done

General mechanism, no shape recognizer. A variant matrix plus must-still-copy
negatives: state read after the update, genuinely aliased state, effectful
sibling expressions whose order would change. Verification by
`--explain-copies` (**flag before the subcommand**) showing the copies gone,
with byte-identical results at O0 and O2.

## Addendum A — minimal reproducer and exact cause, 2026-10-14

Found by mechanical reduction of the real programs rather than by writing
lookalikes, which is what Round 34 got wrong.

**Minimal reproducer, three lines:**

```text
=#b(!buffer(256,0))
(v):v=@(a,0,0;b<64;a[b:b],b+1,c+c(a,b);a)
(v,i)=@(a,b;a[b]!=b;a,a[b];b)
```

```text
{"kind":"replace","bytes":2048,"span":[40,45],
 "retaining_use":[52,58],"reason":"live-root-retention"}
```

`span [40,45]` is the in-place update `a[b:b]`; `retaining_use [52,58]` is the
sibling slot's call `c(a,b)`.

**Exact cause.** Within one loop step, one state slot updates a buffer in place
while **another slot's expression passes the same buffer to a call**. The call
roots its argument for the duration of the call, so at the update the buffer
has two live roots and the in-place path is refused, falling back to the
copying `nil_set`.

**Why Round 34's three probes missed it**, each ruled out by reduction:

| Variant | Copies |
|---|---:|
| No sibling use at all | 0 |
| Sibling reads an element, `a[b]` | 0 |
| Sibling uses the whole buffer without a call, `#a` | 0 |
| Sibling calls a **leaf** function, `(v,i)=a[b]` | 0 |
| Sibling calls a function **containing a loop** | **1** |
| Update inline `a[b:b]` or inside a callee | 1 either way |

The last two rows are the finding. A **leaf** callee is source-expanded —
Round 24's checked source-leaf expansion — so it never takes a root, which is
why `(v,i)=a[b]` does not reproduce while
`(v,i)=@(a,b;a[b]!=b;a,a[b];b)` does. Round 34's probes all used leaf callees
and element reads, so they could not have reproduced it. Candidate 1 from the
main ADR (call-valued index operands) is **not** the cause on its own: the same
union-find shape without the sibling call reports zero copies.

**Candidate 2 is therefore not needed to explain these programs**, which means
this remains intraprocedural and Round 33's "cheaper than believed" reading
stands. ADR 051's interprocedural framing is not reinstated.

**`subtree-of-another-tree`'s 35.3× cliff is a different defect.** Its hints
report `kind: slice`, not `replace`, with `reason: live-root-retention` and a
retaining use at `[345,346]`, and a profile puts **713 of ~760 samples in
`_platform_memmove`**. The cause is the explicit preorder stack: each node does
`!slice(c,0,#c-1)` plus two `!concat`s on a retained buffer, so stack churn is
quadratic. Same reason string, different operation, and not fixed by whatever
fixes the update copy.
