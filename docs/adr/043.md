# ADR 043 — Configurable limits, native stack safety, copy hints and general ownership

## Context

Round 21 starts at main `ab6c1c5` / benchmarks `a3c466b`. Its rule is "generalize,
don't tune": qualification is reported twice, NATURAL (the frozen Round 19
first-attempt sources in `benchmarks/core-generalize-study/natural/`) and TUNED.
The measured baseline is **natural 19/150, tuned 22/150**
([ROUND21_BEFORE.md](../../benchmarks/reports/2026-10-07/ROUND21_BEFORE.md)).
A program that qualifies only after being restructured around compiler internals
is a compiler gap, not a success.

Three measurement results constrain this ADR.

1. **Quota headroom.** The worst admitted reference quota reservation is 3sum at
   **81.29% of 64 MiB** (≈ 52.0 MiB); its live charge is 40.66%. The largest
   natural process RSS is 3sum at **18.47 MiB**. The 64 MiB limit is therefore
   already within 19% of rejecting an admitted program, and Round 20 measured
   3sum's materialized-triple formulation exceeding it outright.
2. **Depth.** No admitted program approaches the 256-frame limit, but eleven
   NeetCode problems are tagged deep-recursion risks and the roadmap holds
   explicit stacks as the only currently proven answer. The reference evaluator
   already heap-allocates frames; the native runtime only checks depth under
   bounded instrumentation.
3. **Copies.** The Part A1 census classifies each physical owning-storage copy
   against later reference-semantic observations
   ([copy_ledger.py](../../benchmarks/core-generalize-study/copy_ledger.py)).
   Its headline group is `PAYLOAD_COPY`; construction, input decode, output
   materialization and growth relocation are reported separately and are never
   folded into it.

`MAX_DYNAMIC_BYTES` is currently a `pub const` in `nil-hir`, and the emitted C
runtime hard-codes `#define NIL_MEMORY_LIMIT UINT64_C(67108864)`. Neither is
reachable from a CLI flag or a library caller today.

## Decision

### (a) Configurable memory and call-depth limits as language semantics

Memory limit and call depth become **declared execution parameters**, not
constants. They are part of a program's observable semantics: the same program
with the same limit must produce the same result, the same diagnostics with the
same codes and spans, and the same host effects on every path.

- **Rust API.** `nil_compiler::evaluator::Limits` gains `memory_bytes: usize`
  alongside the existing `steps` and `call_depth`. `nil_llvm::Options` gains the
  same field. Both keep `Default`, so existing callers compile unchanged.
- **CLI.** `--memory-limit BYTES|<N>MiB` and `--call-depth N` are accepted before
  the command, in the same position as `--bounded`/`--unbounded`. They apply to
  `run`, `build` and `llvm`. `check` and `hir` do not execute and reject them.
- **Native lowering.** The runtime's limit becomes
  `#ifndef NIL_MEMORY_LIMIT / #define NIL_MEMORY_LIMIT ... / #endif` and the
  emitter predefines the configured value in the generated translation unit. The
  depth limit already travels in the runtime context; its initializer changes
  only its value. No runtime code reads a limit it was not given.
- **HIR-level capacity arithmetic** (`collections.rs`, `application.rs`) takes the
  limit as a parameter instead of reading the constant. The constant remains as
  the documented default so no literal changes meaning.

**Defaults, chosen from the A2 evidence.** Memory limit **256 MiB**, call depth
**1024**. 256 MiB is 4.92× the worst observed admitted reservation, which leaves
the largest admitted program below 21% of quota instead of above 81%; it is also
small enough to stay far from host memory on the measurement machine (18.47 MiB
peak RSS). Depth 1024 is 4× the current value, which is reachable without a host
stack overflow in the reference evaluator and is defensible for the recursive
tree and graph problems the roadmap holds out. These defaults are chosen because
headroom was measured, not because a program was observed to need them: **no
currently admitted program requires either increase**, and raising them is
therefore forecast to change no qualification.

**Tests and fuzzing keep the current small limits.** Existing E013 and E008
expectations are part of the validated surface. Every test and both fuzz drivers
pass an explicit `64 MiB` / `256` configuration, so the generated-program codes,
counts and spans are unchanged. A separate, smaller set of tests exercises the
new defaults and the boundary behaviour.

**The reserve-as-if-copying rule stays.** Even an in-place update reserves the
same old-plus-result semantic charge as copying
([ADR 038](038.md), `nil_set_unique_impl`). Removing it would make a program's
E013 boundary depend on whether an ownership proof happened to fire, so adding a
sound ownership improvement could *admit* a program that previously failed, and
losing a proof could reject one that previously passed. That is exactly the
"tuning around compiler behaviour" this round forbids. The rule is therefore
retained unchanged, and the limit is raised instead. Consequence, stated plainly:
peak quota remains roughly twice the live payload for update-heavy programs, so
256 MiB of quota does not mean 256 MiB of usable payload.

**Determinism obligations.** The limit participates in no host query, clock or
allocator feedback. Quota decisions are computed from the configured limit and
the program's own charges only. Reference and native must agree on the admission
decision for the same limit, which the existing differential fuzzing checks.

### (b) Deep recursion without host stack exhaustion

- **Reference.** Frames are already heap-allocated; the evaluator must reach the
  configured depth and raise **E008** (call depth; corrected by ADR 046) at the configured frame, not
  fault. A regression test drives a 1024-deep recursion to completion and a
  1025-deep recursion to the diagnostic.
- **Native.** Stack exhaustion must become a clean **E008** with the existing
  instruction-budget diagnostic text and span, never a segmentation fault. The
  depth counter in the runtime context already provides this under **bounded**
  instrumentation. Unbounded builds currently have no depth check, so raising the
  default depth without a guard would convert a diagnostic into a crash.
  Therefore: unbounded builds gain a **stack-headroom guard** on function entry,
  derived from the thread's stack bounds recorded once at startup, that raises
  E008 before the guard page is reached. The guard is a comparison against a
  cached address, not a system call, and must cost no more than 2% on the three
  historical controls. If the guard cannot meet that cost, the alternative is to
  keep the unbounded default depth at 256 and publish the limitation rather than
  ship a crash.
- No depth policy change is made for earlier profiles or the default profile.

### (c) Copy-hint diagnostic

An opt-in flag, `--explain-copies`, emits machine-readable records to stderr
naming each site where an update copied because the original stayed live. One
record per site per program run:

```
NIL_COPY_HINT <operation> <span-start>..<span-end> kept-live-by <span-start>..<span-end> <kind>
```

Rules: the hint is derived from information the compiler already computes
(last-use and root analyses, plus the emitted copy decision); it names the later
read that keeps the original live; it is deterministic for a given program and
input; and it changes **nothing** observable — exit code, diagnostics, output
bytes, host effects and timing of the unflagged build are all unaffected, because
the flag only enables reporting. Records are ordered by first occurrence. No
program is edited to obtain a hint. Every site named must correspond to a real
copy event, verified against the Part A1 census for the same program and fixture.

### (d) General ownership — the soundness argument and the decision

The target is the census `PAYLOAD_COPY` events classified `AVOIDABLE`: a physical
copy whose source version has no later semantic observation. Two general analyses
were considered, both deliberately shape-independent:

- **G1, interprocedural last-use with alias tracking through callees.** Extend the
  existing last-use proof so a value whose final use is an argument to a callee
  that neither returns an alias of it nor stores it can be treated as uniquely
  owned at the update inside the callee.
- **G2, read-before-write scheduling without structural restriction.** Where
  trap and effect order permit, move a read of the original ahead of the update
  that would otherwise copy, generalizing ADR 039's observed-frame replacement
  beyond flat single-replacement loops.

**Obligations each must discharge.** For every candidate the analysis must prove:

1. *Live aliases.* No other reachable binding observes the pre-update version
   after the update. ADR 038's deferred reconciliation means root counts are
   exact only at observation points, so the proof must be expressed over
   observation points, not over instruction indices.
2. *Returned aliases.* A value returned from a region or callee escapes to a
   caller whose uses are outside the analysed body. G1 must treat any return that
   may alias the argument as a live alias.
3. *Lazy arms.* An unselected arm generates no events, so a read in an unselected
   arm must not count as an observation; a read in a *possibly* selected arm must.
   The analysis must be sound over both selections, i.e. take the union.
4. *Recursion and mutual recursion.* A summary must be a fixed point, not a
   single pass, or a recursive callee can appear not to alias on the first
   iteration.
5. *Record children.* A child held through a parent is observable through the
   parent. Reachability must follow record fields and map values, including a
   child retained only by a live parent.
6. *Trap order.* Moving a read earlier must not move an observable trap earlier
   or later. A read that can trap (bounds, byte range) may only be hoisted past
   operations that cannot trap, and never past a host effect.
7. *Quota observation.* Because the reserve-as-if-copying rule stays, changing a
   copy into a reuse must not change the charge, so E013 boundaries are unchanged
   by construction. Any analysis that also changed the charge would be rejected.
8. *Deferred roots.* The proof must hold for the slot/committed-mirror pair of
   ADR 038 and for the recycled retained slot of ADR 039, including the case
   where copying changed the returned pointer mid-loop.

**Decision: do not ship (d) in Round 21.** Three reasons, in order of weight.

First, **the evidence does not yet support the premise.** The Part A1 census
measures far fewer native payload copies than the cliff magnitudes would require
if copies were the cause. Until the natural-versus-tuned census comparison shows
that the cliff programs' natural forms carry a copy volume proportional to their
slowdown, a general ownership analysis is not demonstrably aimed at the cost.

Second, obligations 1, 2 and 4 interact: a sound interprocedural summary over
observation points with a recursion fixed point is a new load-bearing proof over
the arena, root and quota invariants, which ADR 041's roadmap already flags as
the highest-risk core work. Committing it in the same round as a limits change
would make a divergence impossible to attribute.

Third, rule R2 forbids the cheap substitute. A recognizer that matches the five
cliff sources' shapes would move the timings and would be rejected, so there is
no partial-credit path.

What ships instead: the census, the ledger, the forecasts, and this argument, so
that the next round can start from a measured target rather than an assumption.
If the natural-versus-tuned comparison does show copy volume proportional to the
slowdown, G1 and G2 are re-registered with their variant-shape matrix — reordered
operands, extra bindings versus inline expressions, nested conditionals, reads in
every position relative to the update, aliases through callees, record children
and lazy arms — before any implementation.

## Forecasts

Numeric, falsifiable forecasts for steps 4–6 are preregistered separately in
[FORECASTS.md](../../benchmarks/core-generalize-study/FORECASTS.md), committed
before this ADR's code. In summary: defaults 256 MiB and 1024 frames; all 1,070
NeetCode and 2,815 application checks unchanged; every current E013 reproduced at
the same instruction under a 64 MiB configuration; qualification unchanged by
limits alone at natural 19/150 and tuned 22/150; and (d) forecast not to ship.

## Alternatives

**Raise the constants without making them configurable.** Rejected: it changes
every program's semantics silently and leaves no way to reproduce an old E013.

**Drop the reserve-as-if-copying rule to buy headroom.** Rejected above: it makes
quota depend on whether an optimization fired.

**Make the limit a source-level declaration.** Rejected for this round: it would
add surface syntax to every program and make a program's meaning depend on a
header, which no measurement yet justifies. A library/CLI parameter is enough.

**Grow the native stack instead of guarding it.** Rejected: a larger stack moves
the crash rather than converting it into a diagnostic, and thread stack sizes are
host policy.

**Infer the copy hint from the census overlay.** Rejected: the overlay is
measurement-only instrumentation outside the compiler, so a user-facing hint must
come from the compiler's own analyses.

**Ship a narrower ownership recognizer now.** Rejected by rule R2.

## Consequences

Limits become part of the reported execution configuration, so every report must
state the memory limit and depth it used. The reserve-as-if-copying rule keeps
peak quota near twice live payload. The unbounded stack guard adds a comparison
to every native call in unbounded builds. The copy hint adds a flag and an
output format that must stay stable enough to be machine-read, but carries no
semantic weight. Natural qualification remains the headline, and it is not
expected to move this round. Nothing is pushed.

## Status

Accepted preregistration for (a), (b) and (c). Explicit decision **not** to
implement (d) in Round 21, with the soundness obligations recorded above so a
later round cannot quietly weaken them. Committed before the code it governs.

## Addendum, 2026-10-07: the census contradicts reason #1 for (d)

The Part A1 census completed after this ADR was written. **Its result falsifies
the first and heaviest reason given above for not shipping (d).** The decision not
to ship stands, but on reasons 2 and 3 only, plus budget. The original sentence —
"the census does not yet show native payload-copy volume proportional to the cliff
magnitudes, so the premise is unproven" — is **wrong**, and is corrected here
rather than edited above.

Native O0 payload copies, NeetCode cohorts, summed over every fixture
(`benchmarks/reports/2026-10-07/ROUND21_COPY_CENSUS.json`):

| Cohort | events | copied bytes | strict REQUIRED | strict AVOIDABLE |
|---|---:|---:|---:|---:|
| natural | 6,423,242 | 2,086.6 GB | 2,526,935 (1,926.6 GB) | 3,896,307 (160.1 GB) |
| tuned | 3,945,509 | 105.6 GB | 249,354 (105.5 GB) | 3,696,155 (0.1 GB) |

The Round 20 tuning removed **94.9% of native copied bytes**. The only five
programs whose native payload-copy count differs between the natural and tuned
cohorts are **exactly the five cliff programs**:

| Program | natural events / MB | tuned events / MB | natural REQUIRED | natural AVOIDABLE |
|---|---:|---:|---:|---:|
| last-stone-weight | 1,809,154 / 1,446,604 | 131,891 / 105,306 | 1,809,138 | 16 |
| course-schedule | 500,234 / 399,995 | 7 / 0.0 | 400,228 | 100,006 |
| spiral-matrix | 299,957 / 79,771 | 199,974 / 1.1 | 99,965 | 199,992 |
| balanced-binary-tree | 100,194 / 80,002 | 7 / 0.0 | 100,125 | 69 |
| validate-binary-search-tree | 100,080 / 80,000 | 7 / 0.0 | 0 | 100,080 |

The premise of Part C/D is therefore **confirmed**: the cliffs are copy traffic,
and the natural sources carry it while the tuned sources do not. This is also
direct evidence for rule R1 — each of the three programs that moved from miss to
pass in Round 20 went from 10^5–10^6 copies to **seven**.

The census additionally decides *which* analysis is needed, which the earlier text
could not:

- `validate-binary-search-tree` is **100% AVOIDABLE** (0 of 100,080 REQUIRED). A
  general interprocedural last-use analysis, G1, would remove these.
- `last-stone-weight` is **99.999% REQUIRED** (16 of 1,809,154 AVOIDABLE) and
  `balanced-binary-tree` is 99.93% REQUIRED. Liveness alone cannot touch these:
  the original *is* observed later. Only read-before-write scheduling, **G2**,
  can, which is exactly what the Round 20 binding rewrite did by hand.
- `course-schedule` is 80% REQUIRED and `spiral-matrix` 67% AVOIDABLE, so both
  need G1 and G2.

Consequence for the next round's preregistration: **G2 is the primary target, not
G1**, because G2 covers the largest cliff while G1 alone would leave
last-stone-weight and balanced-binary-tree unchanged. G1 remains worthwhile for
`validate-binary-search-tree`. Both still owe the eight obligations above in full,
and obligation 6, trap order, is the binding constraint on G2 specifically: 
hoisting a read past a possibly-trapping operation is precisely what makes
scheduling unsound. Neither may ship as a shape recognizer.

One disclosed measurement gap: 3sum's largest fixture is excluded from the native
join in both cohorts because its native trace of 6,745,501 events exceeds the
5,000,000 cap. All other 28 programs and all their fixtures are joined in both
cohorts, and the application scope has no exclusions. The fuzz scope of Part A1
is **not achieved**; the report states the cause.

## 2026-10-09 amendment — ADR 047

ADR 047 supersedes exact native stack/call-depth equivalence requirements. Stack
exhaustion is an ordinary resource failure, reported as **E008**, never E010.
Dedicated guarded worker stacks contain exhaustion; non-guard faults remain
crashes. Clean E008/E013 comparisons are inconclusive, not exact semantic claims.
Historical design alternatives above remain historical evidence.
