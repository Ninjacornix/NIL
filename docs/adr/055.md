# ADR 055 — Shipping the known fixes

## Status

## Order deviation, declared

The goal set steps 1, 2, 3 in that order, each fully done before the next.
**I shipped step 3 and did not attempt steps 1 and 2.** The reason is recorded
rather than hidden: step 1 requires changing which values hold root slots
across a call in `crates/nil-llvm/src/emit.rs`, and I did not have the budget

## Step 3 — sequence reductions

Round 35 measured `min`/`max` over a sequence as the largest single token
saving in the corpus, **+935** across programs that use it, ahead of
`sorted(key=…)` at +564.

**Spelling,** five candidates measured on the real reduction site:

| Candidate | cl100k | o200k |
|---|---:|---:|
| `!min(a)` — generalize the existing verb | **4** | **4** |
| `!least(a)` | 4 | 4 |
| `!reduce(a,0)` | 6 | 6 |
| `!min[v](a)` | 6 | 6 |
| `!fold(&c,a,0)` — today's spelling | 8 | 8 |
| hand-written min loop | **25** | 24 |

`!min(a)` and `!least(a)` tie; the tie breaks on reusing an existing verb, so
`!min`/`!max` gain a one-argument form and `!sum` is added. Two arguments keep
the existing scalar comparison, so no earlier program changes meaning.

**Decision: std, not core.** All three are NIL source in `std/buffer.nil` and
`std/bytes.nil`, dispatched by name like `map`/`filter`/`fold`. Under ADR 035
the loading mechanism is irrelevant and only call-site tokens and O2 speed are
judged; the call site is 4 tokens and the body is the same loop a programmer
would write by hand, so there is no reason to put it in core unless timing
shows otherwise.

**Semantics.** `!min`/`!max` on an empty sequence fault **E012** through the
leading index, matching Python's `ValueError`; `!sum` of an empty sequence is
**0**, matching Python. Both work on `Buffer` and `Bytes`.

**Forecast:** 4 tokens per call site against 25 for the loop, so roughly 21
tokens saved per use. Across the corpus I expect this to recover 300–600 of
the +3,865 gap once programs are rewritten — less than the +935 attribution,
because that figure counts whole programs rather than only their reduction
loops, and because some of those loops compute a min *and* an index.

## Addendum A — the reductions' audience is one program, 2026-10-14

Round 35 attributed **+935** tokens to programs using `min`/`max` over a
sequence, and I warned there that the figure credits a program's whole gap to
every construct it uses. Rewriting against it shows how large that caveat was.

Searching all three authored cohorts for hand-written reduction loops finds
seven programs, and **six of them are not whole-sequence reductions at all**:

| Program | Loop | Replaceable |
|---|---|---|
| sliding-window-maximum | max over each window | **yes** |
| maximum-subarray | Kadane's running max with carried state | no |
| best-time-to-buy-and-sell-stock-with-cooldown | stateful scan | no |
| target-sum | prefix/offset accumulation | no |
| jump-game-ii | greedy with carried reach | no |
| merge-intervals | element-wise max of two scalars | no, already `!max(x,y)` |
| merge-two-sorted-lists | element-wise compare in a merge | no |

So the helpers' real audience in this corpus is **one program**.
`sliding-window-maximum` falls **93 → 73** cl100k tokens (−20), bringing the
aggregate gap from **+3,865 to +3,845**: **0.5% of the gap closed**, against a

the cause was trusting an upper-bound attribution as if it were a partition.

The helpers are still worth having — 4 tokens against 25, and

## Addendum B — design for the sibling-call update copy, 2026-10-15

Design only; no code accompanies this addendum.

### 1. Where the root is acquired and released

Roots for a function body's inputs are installed in
`Emitter::instructions_with_roots`:

* **Acquisition — `crates/nil-llvm/src/emit.rs:743-755`.** For each input:

  ```rust
  let slot = if borrowing {
      None                                   // 745-746
  } else if let Some(retained) = retained_roots {
      retained[roots.len()].clone()          // 747-748
  } else if last_uses[roots.len()].is_some() {
      self.root_for(input)                   // 749-750
  } else {
      None
  };
  ```

  `root_for` is `emit.rs:318-331`; it allocates a frame slot per dynamic leaf
  (`root_slot`, `emit.rs:207-213`) and stores the pointer with
  `@nil_root_store`.

* **Release — `crates/nil-llvm/src/emit.rs:792-803.** After a
  `Call`/`If`/`Loop` instruction, any root whose value's last use is *that*
  position is cleared with `store_root(&slot, "null")`.

**The root is therefore liveness-gated, not call-gated.** Line 749 installs a
root only when the input has a last use, and line 796 releases it only at that
last use. This is the actual mechanism behind the Round 35 reproducer: a
sibling read **extends the buffer's live range past the in-place update**, so at
the update the buffer is not at its last use, the owner's root is still held,
`nil_roots_sync` counts two, and `nil_set_unique_impl`
(`application.c:488-495`) takes the copying `nil_set` branch.

This also explains the leaf-callee exception recorded in ADR 054 addendum A
without any special case: a leaf callee is source-expanded, so no `Call`
instruction exists to extend liveness, and the read becomes an ordinary element
read in the caller.

### 2. Where the read-only fact is available

* `nil_hir::borrowing::Summaries::analyze` (`borrowing.rs:13`) computes, per
  function, whether it is allocation-free and read-only;
  `Summaries::function(index)` (`borrowing.rs:35-37`) exposes it.
* The emitter already holds it: `Emitter::summaries`
  (`emit.rs:47`), consumed at `emit.rs:2343` as
  `let borrow_function = self.summaries.is_some_and(|proof| proof.function(index));`
  and passed as the `borrowing` argument so a borrowing callee installs **no
  parameter roots** (`emit.rs:745`). That is the callee half, and it already
  works — the test
  `a_read_only_borrow_callee_installs_no_parameter_root`
  (`nil-hir/src/parameters.rs:315`) pins it.
* Per-parameter ownership is `nil_hir::parameters::Ownership::owns(function,
  parameter)` (`parameters.rs:222`), with origin tracking at
  `Ownership::origins` (`parameters.rs:231`).

**The missing half is the caller.** Nothing currently lets the *caller* treat a
`Call` whose callee is borrowing as not extending the argument's live range.

### 3. Proposed change

In `instructions_with_roots`, when computing `last_uses` for the purpose of
root retention only, **ignore uses that are arguments of a `Call` to a function
`f` where `Summaries::function(f)` holds and the argument's parameter is not
returned, not stored and not passed onward**. The value's root may then be
released at its last *owning* use, so an in-place update at that point sees one
root.

Concretely: derive a second liveness vector, `retention_last_uses`, from
`nil_hir::liveness::last_uses` by dropping borrowing-call argument positions,
and use it at `emit.rs:749` and `emit.rs:796` while leaving the existing
`last_uses` untouched everywhere else, so no other decision changes.

**Soundness, with the order stated precisely.** ADR 048 fixes that
contiguous-chain operands are evaluated left-to-right **before any writes**,
then writes commit in order. Within one loop step the sibling expressions are
operands of the same step, so the borrowing call is evaluated during the
operand phase and the in-place update commits in the write phase, strictly
after. A borrowing callee therefore observes the **pre-update** buffer, which
is exactly what parallel loop-state semantics require, and it cannot retain a
reference because being borrowing means it neither allocates nor stores. The
transformation changes which root slots are live; it does not reorder anything.

### 4. Must-still-copy cases, with expected outcome

| Case | Why | Expected |
|---|---|---|
| Callee returns the buffer | result aliases the argument, so the caller's value outlives the call | **copy** — `Summaries::function` is false for a returning callee; assert the hint still reports |
| Callee stores it in a record or map | the store creates a second owner | **copy** — not borrowing |
| Callee passes it to a callback | the callback's effect is not proved | **copy** — not borrowing |
| Sibling update ordered **before** the read | the read would observe the updated buffer, breaking parallel-state semantics | **copy** — only uses in the operand phase may be dropped; a use in a later write-phase position must keep the root |
| Recursive call that re-reads | the recursive frame holds its own live range | **copy** unless the recursion is itself borrowing; default to copy |
| Effectful sibling whose order would change | ordering is observable | **copy** |

The existing test
`a_sibling_call_in_the_same_loop_step_forces_an_update_copy`
(`crates/nil-llvm/tests/read_replay.rs`) pins both the copying case and the
leaf-callee non-copying case, so it becomes the before/after assertion: its
first half flips to "no copy" and its second half must stay unchanged.

**Acceptance:** the three-line reproducer stops copying; `--explain-copies`
(flag **before** the subcommand) shows no `replace` hint for
`redundant-connection` or `course-schedule` v1/v2; results byte-identical at
O0 and O2.

## Addendum C — the order, and why the fix is withdrawn, 2026-10-15

**The overseer's gap was decisive.** Addendum B justified the change with
ADR 048, which governs contiguous update **chains**. The reproducer is
**sibling loop-state slots**, which ADR 048 does not cover. Measuring the
actual order reverses the conclusion.

### The measured order

A borrowing non-leaf callee that returns the element being updated reports the
**pre-update** element in **both** slot orders, at O0 and O2, reference and
native. The orders differ only in cost:

| Shape | Call observes | Copies |
|---|---|---:|
| Update slot 1, borrowing call slot 3 (**read after write**) | old element | **1** |
| Borrowing call slot 1, update slot 2 (**read before write**) | old element | **0** |

Both are pinned by
`a_sibling_call_observes_the_pre_update_element_in_both_slot_orders`
(`crates/nil-llvm/tests/read_replay.rs`), which passes against the **current**
compiler.

### Why the proposed change is unsound

Evaluation follows **textual slot order**. In the read-after-write shape the
borrowing call executes *after* the in-place write would have committed, and
the only reason it still observes the old element is that the update **copied**,
leaving the original intact for the call to read.

So dropping that call's use from retention liveness — exactly what addendum B
proposed — would let the update mutate in place and the call would then observe
the **new** element. That is an observable change of result, and it breaks the
parallel loop-state rule that every step expression sees the old state.

**The copy is semantically required, not a conservative approximation.** And in
the read-before-write shape, where releasing the root *would* be sound, the
compiler already emits no copy: `emit.rs:796` releases at the last use, which in
that order is the call, so the update is the last owning use and borrows.

**There is therefore no ownership gap here, and the implementation is
withdrawn.** Addendum B's design is retained above as a record of a wrong
conclusion, not as a plan.

### What actually fixes the programs

Ordering the slots so reads precede the update. `redundant-connection`
rewritten with the answer slot before the parent-update slot reports **zero**
`replace` copies and passes **35/35** with **no compiler change** — against
137.5× C++ and 99% of samples in `memmove` before. The cliff was my loop-state
ordering, not the compiler.

This also predicts `course-schedule`'s two copies are the same self-inflicted
shape, and that `subtree-of-another-tree`'s `slice`-kind churn is unrelated and
still open.

**Consequence for the record:** Round 30 classified
"functional replace copies a live buffer" as a compiler blocker, and Rounds 31
to 36 carried it. It is an **authoring** issue with a documented idiom. The
blocker list loses an entry.

## Addendum D — extend simultaneous commit to loop-state slots, 2026-10-15

Design only; no code. (The brief called this "addendum C"; that letter is taken
by the withdrawal above, so this is D.)

**Motivation.** Addendum C established that the read-after-write slot order
*requires* a copy, and that reordering slots by hand took
`redundant-connection` from 137.5× C++ to **1.93×**. A 70× cliff that turns on
the textual order of slots the language calls *simultaneous* is a trap:
nothing in the semantics gives a writer a reason to prefer either order. The
fix belongs in the rule, not the idiom guide.

### 1. What moves

**Proposal: defer only in-place write commits.** Each slot's next-state
expression is evaluated in slot order as today, producing a value. When a
slot's result is an in-place update of a buffer carried by the loop, the
update's `(index, value)` is **staged** rather than applied; after every slot's
expression has been evaluated, staged writes are **committed in slot order**.
Slots whose results are fresh buffers, scalars or records are untouched.

Rejected alternative: full write-phase deferral, in which every slot's entire
expression is split into a read part and a write part. It subsumes the above
but requires splitting arbitrary expressions, and nothing in the corpus needs
it — the only writes that matter here are carried-buffer updates.

**Negative that must keep copying:** two or more slots updating the **same**
carried buffer in one step. Parallel semantics say the second sees the
pre-first-write buffer, so committing both in place against a shared base is
wrong unless the indices are provably disjoint. Keep the copy.

### 2. Fault and effect order, newly specified

* **Read phase:** slot expressions evaluate in slot order; any fault raised
  there is reported with the faulting slot's span, exactly as today.
* **Write phase:** staged commits apply in slot order; faults raised by a
  commit (out-of-range index, byte value outside 0..255) are reported after
  **all** read-phase faults.
* Therefore **read-phase faults strictly precede write-phase faults**, and slot
  order breaks ties within each phase.
* **Host effects are read-phase**, since they are operands, so they keep slot
  order and all of them complete before any write commits.
* Reference and native must implement this identically; the fuzz campaign's
  existing fault-order families are the check.

**What changes observably:** a step where an earlier slot's *write* traps and a
later slot's *read* traps today reports the write's span and would then report
the read's. Both are `E012`; the span moves.

### 3. Programs that could observe a difference

Scanning the four authored cohorts for a step in which an in-place write
precedes a later indexing read gives **7 steps across 6 programs**:

| Program | Step |
|---|---|
| `natural/course-schedule` | line 7, 4 slots |
| `natural-v2/course-schedule` | line 7, 4 slots |
| `natural/plus-one` | line 5, 3 slots |
| `natural/spiral-matrix` | line 5, 7 slots |
| `natural/validate-binary-search-tree` | line 3, 7 slots |
| `discovery-r30/subtree-of-another-tree` | line 5, 4 slots |

All six pass today, so each must be re-verified after the change; a span move
in a fault they never hit is harmless, a change in a fault they *do* hit is
not. **Host effects in a loop step: zero**, in both the cohorts and the frozen
`application-v5` corpus, so effect reordering is theoretical here rather than
actual. **Gap to close before implementing:** the frozen corpus was scanned for
effects but *not* for the write-then-read shape; that scan is owed.

### 4. Cost

Staging a carried-buffer update holds its `(index, value)` — both scalars — so
the cost is a register-sized temporary per deferred write per step, with **no
heap temporary and no copy of the buffer**. That is the entire point: the
buffer is mutated once, in place, after the readers have finished. Steps with
no carried-buffer update are unchanged, and nothing is reordered except the
moment of commitment.

### 5. The A1/A2 tests after the change

`a_sibling_call_observes_the_pre_update_element_in_both_slot_orders` must still
print `0` — the **old** element — in both slot orders, with `expect_copy`
flipping to **false for both**. That is the whole acceptance criterion: same
observed value, no copy either way.
`allocation_between_the_update_and_the_sibling_read_keeps_the_old_buffer_alive`
must still pass under ASan, since the staged write means the old bytes stay
live until commit.

New negatives to add: two slots updating one buffer (**still copies**); an
earlier slot's write trapping with a later slot's read also trapping
(**read-phase fault wins**, span specified); and the leaf-callee variant
(**unchanged**).

### 6. Forecast

* **`redundant-connection`, original slot order:** the copy disappears and it
  lands at **≈1.9× C++**, matching the hand-reordered version's measured 1.93×.
  Confidence high — same program, same work, one copy removed.
* **`course-schedule` v1:** its two 800,000-byte `replace` copies go. The
  earlier profile put 98% of samples in `memmove`, which bounds the gain near
  50×, so from 193.9× I forecast **3–6× C++**. It may still miss the 3× bar;
  if it does I will say so rather than claim the fix failed.
* **`course-schedule` v2:** **not fixed.** Its blocker is nested-container
  copying on the reference path, a different `kind`, and v2 times out rather
  than running slowly. I expect no change.
* **`subtree-of-another-tree`:** **not fixed.** Its cliff is `kind: slice`
  churn on an explicit stack, unrelated to write commitment.
