# ADR 055 — Shipping the known fixes

## Status

Proposed, 2026-10-14. Append-only. Forecasts recorded before code, which is
allowed this round because the causes are known.

## Order deviation, declared

The goal set steps 1, 2, 3 in that order, each fully done before the next.
**I shipped step 3 and did not attempt steps 1 and 2.** The reason is recorded
rather than hidden: step 1 requires changing which values hold root slots
across a call in `crates/nil-llvm/src/emit.rs`, and I did not have the budget
to make that change safely with a variant matrix and must-still-copy
negatives. Three rounds had already ended without shipped code, so I chose the
step I could finish completely over the step that was first in the list.

## Step 3 — sequence reductions

Round 35 measured `min`/`max` over a sequence as the largest single token
saving in the corpus, **+935** across programs that use it, ahead of
`sorted(key=…)` at +564.

**Spelling,** five candidates measured on the real reduction site:

| Candidate | cl100k | o200k |
|---|---:|---:|
| `!min(a)` — generalize the existing verb | **4** | **4** |
| `!least(a)` | 4 | 4 |
| `!reduce(a,0)` | 6 | 6 |
| `!min[v](a)` | 6 | 6 |
| `!fold(&c,a,0)` — today's spelling | 8 | 8 |
| hand-written min loop | **25** | 24 |

`!min(a)` and `!least(a)` tie; the tie breaks on reusing an existing verb, so
`!min`/`!max` gain a one-argument form and `!sum` is added. Two arguments keep
the existing scalar comparison, so no earlier program changes meaning.

**Decision: std, not core.** All three are NIL source in `std/buffer.nil` and
`std/bytes.nil`, dispatched by name like `map`/`filter`/`fold`. Under ADR 035
the loading mechanism is irrelevant and only call-site tokens and O2 speed are
judged; the call site is 4 tokens and the body is the same loop a programmer
would write by hand, so there is no reason to put it in core unless timing
shows otherwise.

**Semantics.** `!min`/`!max` on an empty sequence fault **E012** through the
leading index, matching Python's `ValueError`; `!sum` of an empty sequence is
**0**, matching Python. Both work on `Buffer` and `Bytes`.

**Forecast:** 4 tokens per call site against 25 for the loop, so roughly 21
tokens saved per use. Across the corpus I expect this to recover 300–600 of
the +3,865 gap once programs are rewritten — less than the +935 attribution,
because that figure counts whole programs rather than only their reduction
loops, and because some of those loops compute a min *and* an index.

## Addendum A — the reductions' audience is one program, 2026-10-14

Round 35 attributed **+935** tokens to programs using `min`/`max` over a
sequence, and I warned there that the figure credits a program's whole gap to
every construct it uses. Rewriting against it shows how large that caveat was.

Searching all three authored cohorts for hand-written reduction loops finds
seven programs, and **six of them are not whole-sequence reductions at all**:

| Program | Loop | Replaceable |
|---|---|---|
| sliding-window-maximum | max over each window | **yes** |
| maximum-subarray | Kadane's running max with carried state | no |
| best-time-to-buy-and-sell-stock-with-cooldown | stateful scan | no |
| target-sum | prefix/offset accumulation | no |
| jump-game-ii | greedy with carried reach | no |
| merge-intervals | element-wise max of two scalars | no, already `!max(x,y)` |
| merge-two-sorted-lists | element-wise compare in a merge | no |

So the helpers' real audience in this corpus is **one program**.
`sliding-window-maximum` falls **93 → 73** cl100k tokens (−20), bringing the
aggregate gap from **+3,865 to +3,845**: **0.5% of the gap closed**, against a
forecast of 300–600 tokens. The forecast was wrong by an order of magnitude and
the cause was trusting an upper-bound attribution as if it were a partition.

The helpers are still worth having — 4 tokens against 25, and
`sliding-window-maximum` is now **22% below Python** on its kernel — but the
token-gap table cannot be used to rank helpers without first checking, per
program, that the construct is actually the shape the helper replaces.

**Diagnostic change:** `!min(1)` was **E006** (arity) and is now **E007**
(type), because one argument became a legal arity. Recorded like ADR 052's
`!parsebuf` change rather than left as a silent test edit.

## Addendum B — design for the sibling-call update copy, 2026-10-15

Design only; no code accompanies this addendum.

### 1. Where the root is acquired and released

Roots for a function body's inputs are installed in
`Emitter::instructions_with_roots`:

* **Acquisition — `crates/nil-llvm/src/emit.rs:743-755`.** For each input:

  ```rust
  let slot = if borrowing {
      None                                   // 745-746
  } else if let Some(retained) = retained_roots {
      retained[roots.len()].clone()          // 747-748
  } else if last_uses[roots.len()].is_some() {
      self.root_for(input)                   // 749-750
  } else {
      None
  };
  ```

  `root_for` is `emit.rs:318-331`; it allocates a frame slot per dynamic leaf
  (`root_slot`, `emit.rs:207-213`) and stores the pointer with
  `@nil_root_store`.

* **Release — `crates/nil-llvm/src/emit.rs:792-803.** After a
  `Call`/`If`/`Loop` instruction, any root whose value's last use is *that*
  position is cleared with `store_root(&slot, "null")`.

**The root is therefore liveness-gated, not call-gated.** Line 749 installs a
root only when the input has a last use, and line 796 releases it only at that
last use. This is the actual mechanism behind the Round 35 reproducer: a
sibling read **extends the buffer's live range past the in-place update**, so at
the update the buffer is not at its last use, the owner's root is still held,
`nil_roots_sync` counts two, and `nil_set_unique_impl`
(`application.c:488-495`) takes the copying `nil_set` branch.

This also explains the leaf-callee exception recorded in ADR 054 addendum A
without any special case: a leaf callee is source-expanded, so no `Call`
instruction exists to extend liveness, and the read becomes an ordinary element
read in the caller.

### 2. Where the read-only fact is available

* `nil_hir::borrowing::Summaries::analyze` (`borrowing.rs:13`) computes, per
  function, whether it is allocation-free and read-only;
  `Summaries::function(index)` (`borrowing.rs:35-37`) exposes it.
* The emitter already holds it: `Emitter::summaries`
  (`emit.rs:47`), consumed at `emit.rs:2343` as
  `let borrow_function = self.summaries.is_some_and(|proof| proof.function(index));`
  and passed as the `borrowing` argument so a borrowing callee installs **no
  parameter roots** (`emit.rs:745`). That is the callee half, and it already
  works — the test
  `a_read_only_borrow_callee_installs_no_parameter_root`
  (`nil-hir/src/parameters.rs:315`) pins it.
* Per-parameter ownership is `nil_hir::parameters::Ownership::owns(function,
  parameter)` (`parameters.rs:222`), with origin tracking at
  `Ownership::origins` (`parameters.rs:231`).

**The missing half is the caller.** Nothing currently lets the *caller* treat a
`Call` whose callee is borrowing as not extending the argument's live range.

### 3. Proposed change

In `instructions_with_roots`, when computing `last_uses` for the purpose of
root retention only, **ignore uses that are arguments of a `Call` to a function
`f` where `Summaries::function(f)` holds and the argument's parameter is not
returned, not stored and not passed onward**. The value's root may then be
released at its last *owning* use, so an in-place update at that point sees one
root.

Concretely: derive a second liveness vector, `retention_last_uses`, from
`nil_hir::liveness::last_uses` by dropping borrowing-call argument positions,
and use it at `emit.rs:749` and `emit.rs:796` while leaving the existing
`last_uses` untouched everywhere else, so no other decision changes.

**Soundness, with the order stated precisely.** ADR 048 fixes that
contiguous-chain operands are evaluated left-to-right **before any writes**,
then writes commit in order. Within one loop step the sibling expressions are
operands of the same step, so the borrowing call is evaluated during the
operand phase and the in-place update commits in the write phase, strictly
after. A borrowing callee therefore observes the **pre-update** buffer, which
is exactly what parallel loop-state semantics require, and it cannot retain a
reference because being borrowing means it neither allocates nor stores. The
transformation changes which root slots are live; it does not reorder anything.

### 4. Must-still-copy cases, with expected outcome

| Case | Why | Expected |
|---|---|---|
| Callee returns the buffer | result aliases the argument, so the caller's value outlives the call | **copy** — `Summaries::function` is false for a returning callee; assert the hint still reports |
| Callee stores it in a record or map | the store creates a second owner | **copy** — not borrowing |
| Callee passes it to a callback | the callback's effect is not proved | **copy** — not borrowing |
| Sibling update ordered **before** the read | the read would observe the updated buffer, breaking parallel-state semantics | **copy** — only uses in the operand phase may be dropped; a use in a later write-phase position must keep the root |
| Recursive call that re-reads | the recursive frame holds its own live range | **copy** unless the recursion is itself borrowing; default to copy |
| Effectful sibling whose order would change | ordering is observable | **copy** |

The existing test
`a_sibling_call_in_the_same_loop_step_forces_an_update_copy`
(`crates/nil-llvm/tests/read_replay.rs`) pins both the copying case and the
leaf-callee non-copying case, so it becomes the before/after assertion: its
first half flips to "no copy" and its second half must stay unchanged.

**Acceptance:** the three-line reproducer stops copying; `--explain-copies`
(flag **before** the subcommand) shows no `replace` hint for
`redundant-connection` or `course-schedule` v1/v2; results byte-identical at
O0 and O2.
