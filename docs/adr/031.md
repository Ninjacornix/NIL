# ADR 031 — Proved bulk-comparison lowering and builder debt

## Context

The validated, borrowing-only equality provider replaced an optimized `memcmp`
with an element loop: reported 16 MiB O2 cost rose from 7.23 to 16.96 ms.
Record-field append and nested builders also remain superlinear. No new language
surface is needed to investigate these debts.

## Decision

Recognize a **proved HIR idiom**, not a plugin ID, name, file, declaration or
unchecked semantic promise. The initial idiom is full equality of two Bytes or
Buffer parameters: compare lengths, start at index zero with equality true,
continue while index is below length and equality remains true, compare the two
indexed elements, advance by one, and return the equality accumulator. All
executed instructions must be accounted for; extra traps/effects and altered
bounds, steps or exit results reject the optimization. Equivalent instruction
ordering and source spans must not matter. Any third-party validated provider
with this body receives the same lowering. Unknown algorithms retain ordinary
provider compilation. This is compiler idiom recognition, not arbitrary automatic
optimization of every plugin algorithm.

Use a private nonallocating native bulk comparison (length guard then `memcmp`).
All i64 bit patterns have unique integer equality representations; Bytes have
unsigned byte equality. Empty inputs must not access payload. Length mismatch
must not access elements. Valid arena payload and length invariants prove that
full comparison has no observable bounds trap. Integer index advancement cannot
overflow at the 64 MiB limit. Provider execution has no caller fuel/depth cost;
argument evaluation and its failures stay in their original order. Reference
execution continues to interpret the validated provider body. Borrowing/effect
summaries remain derived from that body, never from recognition or a manifest.
No floating, record, keyed or partial-range comparison is admitted.

Diagnose record-field append with unchanged IR and runtime-only paired controls,
assembly and explicit copy/root/collection work counts before changing builders.
Attempt field/parent retention only where existing aliases, allocation-boundary
liveness and conservative copy quota reservations can be preserved. Do not treat
an extracted field as unique while its still-live parent or another field owns an
alias. Keep conservative paths and publish measured scaling where proof fails.

## Alternatives

An unchecked `bulk_equal` manifest promise can lie about traps/ordering. A special
case for shipped ID zero privileges one provider. Relying on inlining alone does
not recover optimized library comparison. All are rejected. General field-sensitive
or edge-incremental liveness may be future work if current proofs cannot admit it.

## Consequences

No surface/types/intrinsics/dependencies/default-profile change. Native optimization
has an independently testable proof and reference oracle. Third-party examples and
near-miss rejection tests are required. Builders may remain expensive; reporting an
explained conservative limit is preferable to unsound reuse.

## Status

Accepted for implementation; builder reuse outcomes remain experimental until measured.

## Implemented builder proofs

A later scalar/other-field read of the old record is permitted only if there is
no allocation from concat through the last such read. The overwritten field itself
cannot be read, escaped or returned again. The projected operand/result have one
consumer each, and concat is immediately followed by its field overwrite. Root
transfer preserves all other field, caller and arena-parent aliases. Runtime
uniqueness and the existing copy-equivalent quota reservation still decide reuse.

Direct final concat state can retain its root across an allocation-free condition
and straight-line allocating body. Temporaries still obey ordinary last-use roots;
nested allocating regions and calls stay conservative. The result recycles its
operand's slot, preventing a zero-root transition for a reused parent and hence
avoiding a scan of all existing child edges on every append.

Native arena reclamation is deferred while the requested physical reservation
already fits 64 MiB. If it does not, collect dead entries before checking quota.
`nil_allocated` bounds physical arena capacity including dead entries; `nil_live`
and existing conservative result reservations continue to define semantic E013.
No allocation that previously failed quota is admitted: when physical space fits,
live space necessarily fits; otherwise collection yields the same live set as the
old eager sweep. Growth still collects before locating and relocating its root.
This avoids an arena-list walk per tiny allocation, without a new memory model.

## Sweep-policy correction found by controls

Deferring all sweeps until physical exhaustion made copy-heavy keyed repacking
and nested-field updates slower: dead large payloads accumulated between copies.
Keep that failed-policy measurement in the report. Collect earlier when garbage
(`nil_allocated - nil_live`) reaches `max(64 KiB, nil_live / 4)`, or whenever the
next reservation needs physical space. Growing live graphs still have
geometrically spaced sweeps; copied large dead payloads trigger prompt cleanup.
This bounds garbage working-set growth without changing live charges, the 64 MiB
physical arena cap, conservative copy reservations or any diagnostic ordering.

## Flat-arena specialization

The live-relative policy still cost ordinary 1 MiB append roughly 6% in a
40-repeat paired control (23.851 → 25.271 ms). Reuse the existing closed-world
`NIL_RECORD_BUFFERS` proof: without record buffers, heap allocations have no child
edges (record dynamic leaves are direct SSA roots; keyed values are packed inline).
Keep the established eager sweep for that flat arena, including prompt allocator
reuse. Child-aware/mixed programs use the bounded deferred policy. This is a
validated type/property selection, not a benchmark/function-name exception.
A 25-repeat prototype restores the flat path (24.303 → 22.331 ms); final gates
and controls are repeated after the specialization. Live accounting, the physical
cap, copy-equivalent reservation and observability remain unchanged.
