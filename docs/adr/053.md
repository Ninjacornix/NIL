# ADR 053 — Nested container values, and a retraction

## Status

Proposed, 2026-10-14. Forecasts recorded **before** any code. Append-only.

## Step 1 — retraction: the copy instrument has no blind spot

**This is a retraction of my own finding, repeated across three rounds.**

ADR 051 addendum A recorded that `--explain-copies` fails to report the
`roots == 2` unique-update fallback copy, and called it "a defect that makes
any copy claim from it unreliable, including earlier rounds'". Round 30 listed
it as a blocker, Round 31 and Round 32 repeated it, and this round's goal
treated fixing it as a prerequisite.

**The instrument was always correct. My command line was wrong.** The CLI usage
is `nil [--profile P] [--explain-copies] run FILE`, with the flag **before** the
subcommand. I had been writing `nil --profile expr-v5 run --explain-copies
FILE`, which fails argument parsing, prints `E010 invalid arguments` and exits
without running the program. I read the resulting absence of hints as a
compiler defect rather than as a usage error, three rounds running, without
once checking the exit status or the stderr I was grepping.

Run correctly, both programs report the copy with site, reason **and** the
retaining root:

```text
course-schedule v1, largest fixture
  {"kind":"replace","bytes":800000,"span":[710,727],
   "retaining_use":[783,784],"precision":"root-retention-use",
   "reason":"live-root-retention"}
  {"kind":"replace","bytes":800000,"span":[750,760],
   "retaining_use":[783,784], … same reason}

redundant-connection, largest fixture
  {"kind":"replace","bytes":800000,"span":[320,335],
   "retaining_use":[220,235],"precision":"root-retention-use",
   "reason":"live-root-retention"}
```

The retaining pattern is identical in both: an update whose buffer is still
reachable from a **live loop-state root** declared earlier in the same
function, so the update cannot borrow and falls back to `nil_set`, which copies
and reports `kind: replace` with `reason: live-root-retention`.

**Consequences.** No instrument work is needed. The earlier copy figures are
*not* unreliable; that claim is withdrawn. ADR 051 addendum A is corrected by
its own addendum C. What remains true is the underlying performance problem:
`redundant-connection` is 137.5× C++ with 99% of samples in `memmove`, and
`course-schedule` v1 copies ~5.2 GB. The cause was never hidden — it was
reported all along and I failed to read it.

The only deliverable for step 1 is therefore a regression test asserting that a
`roots == 2` update copy is reported with its site, reason and retaining root,
so this cannot be mistaken again.

## Step 2 — nested container values

What the six nesting-blocked problems' natural Python actually needs, read
before designing:

| Problem | Operation | Shape |
|---|---|---|
| time-based-key-value-store | `records.setdefault(k,[]).append((t,v))` | map → growable list of pairs |
| design-twitter | `posts.setdefault(u,[]).append(…)`, `follow[u]` as a set | map → growable list; map → set |
| design-add-and-search-words | `node.setdefault(x,{})` | map → map (trie) |
| subtree-of-another-tree | serialized tree compare | rows of bytes |
| serialize-and-deserialize-binary-tree | iterative codec over node rows | rows of bytes |
| (sixth, `word-search`, is already solved by splitting) | — | — |

So the required set is **map values that hold a sequence**, plus **map values
that hold a map** for the trie. Two of the six want only rows of bytes, which
`!split` plus `!slice` may already cover — that should be checked before any
type work, because it would cut the feature's audience from 6 to 3.

**Decision direction:** map values may hold a sequence; appending to the value
under a key updates in place when the map is uniquely owned, expressed as
take-value, update-uniquely, put-back, with child-edge transfer confined to a
single function. Interprocedural transfer only if a target problem needs it.

**Spelling:** reuse `!put`/`!get`, with at least three measured candidates for
the append-under-key operation.

**Forecast:** 2–3 of the three genuinely nesting-blocked problems become
expressible; the trie is the least certain because a map-valued map needs the
child edge to nest two deep. I do **not** forecast that this fixes
`course-schedule` v2 or `redundant-connection`, whose copies are caused by live
loop-state roots in the same function, not by nesting.

## What would falsify the plan

If `subtree-of-another-tree` and `serialize-and-deserialize-binary-tree` turn
out to be expressible with `!split` alone, then nesting's audience is 3, not 6,
and it is no longer clearly the top blocker — in which case the honest move is
to say so and re-rank before building a type-system feature.

## Addendum A — the falsification test fired; nesting's audience is three, 2026-10-14

Written **before** any step-2 code, as the ADR requires.

Reading the two tree problems' natural Python shows **neither needs nested
containers**:

* `subtree-of-another-tree` parses node rows with `Numbers(data)`, flattens
  both trees to **flat token sequences**, and runs KMP over them. Flat i64
  buffers and integer links, both available since Round 24.
* `serialize-and-deserialize-binary-tree` parses node rows and joins the token
  sequence, substituting `#` for null. That is string building over a flat
  buffer, not nesting.

So the six-problem figure for nesting was wrong, and it was wrong the same way
Round 30's seven-problem figure for tokenization was wrong: **a problem that
*mentions* trees is not a problem that needs a tree type.** Nesting's real
audience is the **three design problems** —
`time-based-key-value-store`, `design-twitter` and
`design-add-and-search-words-data-structure`.

**The corrected picture across Round 30's fifteen classified problems:**

| Blocker | Problems |
|---|---:|
| Nested/sequence-valued map values | **3** |
| Worklist or deque under parallel loop state | **3** |
| **No blocker — simply unwritten** | **5** |

The five unwritten ones are `subtree-of-another-tree`,
`serialize-and-deserialize-binary-tree`, `combination-sum` (unblocked by the
Round 31 `!parsebuf` fix), `merge-intervals` and `multiply-strings`.

**Decision: step 2 is not built this round.** Nothing is a top blocker at more
than three problems, and five problems need no compiler work at all. Building a
type-system feature for three problems ahead of writing five that need nothing
would repeat exactly the mistake the discovery round was created to stop. The
claim is demonstrated rather than asserted: one of the supposedly
nesting-blocked tree problems is written this round with no new feature.

Nesting remains the right next *feature* when features are what is needed. It
is not the right next *action*.
