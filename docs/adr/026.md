# ADR 026 — Core semantics and compiler-visible extensions

## Context

The core must remain small, but an opaque ABI call hides allocation, alias and
reuse contracts. Sort/each are useful without establishing that every library
algorithm belongs permanently in HIR. The STL analogy supports compiler-visible
implementation, not an opaque runtime boundary. ADR 017 defers stable ABI; scalar
types and records must precede its type/effect/lifetime contract.

## Decision

Proof participation is a **visibility requirement, not sufficient reason for a
permanent core opcode**. An operation belongs in core when it defines fundamental
typed value/control/storage semantics, or no smaller semantic contract can expose
its lifetime, alias, reuse, quota, trap and effect behavior without losing the
existing observational guarantees. Prefer a small primitive over an algorithm.

A future extension can move an algorithm out only when its typed signature,
allocation/borrow/escape/effect/trap-order summaries and deterministic lowering
are visible to validation and optimization. Compiler-visible lowering/static
linking is allowed; opaque dynamic dispatch is not assumed equivalent. A scalar
nonallocating function is not charged root traffic just because it lives outside
core. Reject untrusted/insufficient summaries conservatively. Core guarantees
cannot depend on a plugin's undocumented behavior. No ABI or migration this round.

Every existing intrinsic is classified below. “Retain” refers to its semantic
contract; implementation code need not live in the frontend. “Outward” is
conditional on an equivalent compiler-visible extension, not approved migration.

| Intrinsic | Proof/semantic role | Future placement |
|---|---|---|
| buffer | Owned typed storage, fill, capacity/quota | Retain generic constructor contract |
| bytes | Owned byte storage, byte range/capacity | Retain generic constructor contract |
| concat | Owned result, alias-preserving append reuse/growth | Retain storage contract |
| slice | Owned result/copy, quota/lifetime | Retain until equivalent owned-copy lowering |
| map | Typed owned keyed storage layout/capacity | Retain storage/type contract |
| bytemap | Typed owned keyed byte-value storage | Retain storage/type contract |
| insert | Unique update, duplicate-before-quota, deterministic order | Retain keyed update contract |
| put | Unique update/repack, alias and capacity proofs | Retain keyed update contract |
| get | Borrow integer or allocate owned bytes, missing-before-quota | Retain typed lookup/lifetime contract |
| key | Owned copy, index-before-quota, ordered traversal | Retain traversal/copy contract |
| size | Nonallocating immutable metadata read | Retain generic length contract |
| has | Nonallocating keyed search | Outward with borrowed read-only summary/lowering |
| sort | Algorithm plus full-capacity reservation and unique reuse | Outward only with equivalent reorder/reuse/quota lowering |
| equal | Borrowed read-only comparison | Outward with typed borrowed lowering |
| find | Borrowed read-only search, bounds/byte trap order | Outward preserving checks and borrowed lowering |
| parsebuf | Parsing algorithm, owned buffer/result reservation | Outward with visible allocation/check order |
| format | Numeric/text algorithm, owned byte allocation | Outward with allocation and exact numeric-text contract |
| parse | Text algorithm, scalar result/checked failure | Outward with nonallocating/trap summary |
| read | Host capability, owned result, I/O/quota order | Outward operation/provider; core effect/owned-result contract remains |
| write | Ordered host effect and checked I/O | Outward operation/provider; core effect-call contract remains |
| out | Ordered host effect and checked I/O | Outward operation/provider; core effect-call contract remains |

Each is syntax lowering to core Loop, not an intrinsic or iterator object. Numeric
arithmetic, comparisons, explicit conversions, SSA control and type identity are
core contracts. Numeric text parsing/formatting extensions receive the same
conditional placement as existing parse/format. Bit observation/construction is a
core representation contract. No user plugin syntax, borrowed views or opaque ABI.

## Alternatives

“Any allocation/effect stays core” admits virtually every application operation
and cannot bound growth. “All algorithms behind an ABI” recreates abstraction
cliffs and hides traps/roots. Header/static/compiler-visible libraries are the
appropriate comparison, but their future interface still needs validation.

## Consequences

Current operations stay where they are. Future proposals must state which core
primitive/contract they need, why existing lowering is insufficient, and whether
an extension can provide the required visibility. This criterion does not authorize
new algorithms or migration. Stable ABI remains deferred until records/type and
lifetime contracts exist.

## Status

Accepted policy before numeric implementation. No migration in this goal.
