# ADR-006: Initial parser and surface profile

## Context

design.md prefers nested prefix expressions; report.md demonstrates line instructions with implicit result IDs. Neither supplies NIL generation benchmarks.

## Decision

Plan one handwritten line parser with numeric function/value IDs, const/add/sub/mul/div/call/ret, explicit signatures and end delimiters. Newlines delimit call arguments independently of callee lookup. Call arity is checked after all signatures are collected.

## Alternatives

Nested fixed-arity prefix trees; S-expressions; numeric opcodes; parser generator. Compare profiles at M7.

## Consequences

No operator precedence or destination syntax. Some source tokens may be wasted; that is acceptable for an unmeasured reference profile. Preserve the conflict in PROJECT_STATE.md rather than declaring report.md authoritative on syntax.

## Status

Proposed experiment; no syntax winner selected.

## Implementation update (2026-09-29)

The paired three-program study now exists in `benchmarks/paired/results/2026-09-29/`.
It found fewer raw source tokens for expr-v0 than lines-v0 on those arithmetic
fixtures under both recorded tokenizers. Accordingly, expr-v0 is now the default
API/CLI profile; lines-v0 remains selectable. This updates the prototype default,
not the unresolved long-term syntax decision. The study does not measure model
success, repairs or TCR.
