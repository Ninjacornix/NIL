# ADR 052 — Text toolkit and an honest copy instrument

## Status

Proposed, 2026-10-14. Forecasts recorded **before** any code. Append-only:
corrections go in addenda, not edits.

## Why

Round 30 stopped choosing work by forecast and measured it instead. Of 25
held-out problems, the blocker histogram was:

| Blocker | Problems |
|---|---:|
| Missing text tokenization | **7** |
| Parallel loop state blocks deques/worklists | 3 |
| Missing sequence-valued containers | 3 |
| Per-element `!concat` row join | 2 |
| `!parsebuf` empty-field intolerance | 1 blocked + 4 taxed |
| Functional replace copies a live buffer | 1 |

This ADR takes the first, fourth and fifth of those, plus the instrument defect
that hid the sixth. It deliberately does **not** take the ownership work.

## Step 0 — `!parsebuf` must accept empty fields

`!parsebuf` emits one value per separator occurrence, plus a trailing field
when the last byte is not a separator. The corpus encodes an empty vector as
`"0 \n"`, which yields the fields `"0"` and `""`, and the empty one fails
**E016 invalid decimal i64**.

**`parse_decimal("")` is unconditionally an error today, so no working program
can depend on an empty field.** Skipping empty fields is therefore strictly
more permissive and cannot change the meaning of any program that currently
runs. That is the whole compatibility argument, and it is why this is a bug fix
rather than a profile change.

**Decision:** empty fields are skipped. `"0 \n"` yields `[0]`; a run of
separators behaves like one; leading and trailing separators contribute
nothing; all-separator input yields an empty buffer. This matches Python's
no-argument `.split()`, which is what the corpus assumes.

**Forecast:** the 169-token hand-written scanner disappears from three authored
programs and unblocks `combination-sum`.
`longest-increasing-subsequence` 266 → ~110 tokens, `merge-two-sorted-lists`
352 → ~190. No speed change beyond removing a linear pass.

## Part 1 — text toolkit

### 1a. Splitting

The blocked problems need tokens, and NIL has **no sequence-of-byte-strings
type** — nested containers are the long-deferred gap. Rather than introduce
one, the plan is to return **token offsets into the original bytes**: a split
yields a `Buffer` of alternating offset and length pairs, and an individual
token is recovered with the existing `!slice`. No new type, no nested
ownership, one allocation per call.

**Forecast:** tokenizing costs roughly `!split(a," \n")` plus
`!slice(a,t[2*i],t[2*i+1])` per token, about 12 and 14 tokens. Against
Python's `.split()` at 3 tokens this still loses, but it makes seven problems
expressible where they are now impossible. I expect 3–5 of the 7 to qualify;
`design-twitter` and `design-add-and-search-words` probably still need
sequence-valued containers for their persistent state, so I expect them to
stay blocked.

### 1b. Joining

The row join is the worst token hot spot: **40 tokens against Python's 7**, and
its per-element `!concat` is also the cliff behind `counting-bits` (4.60× C++)
and `merge-two-sorted-lists` (3.47×).

**Decision direction:** generalize `!format` rather than add a verb, so a
numeric sequence becomes one separated row in a single call that sizes the
output first and fills it once.

**Forecast:** 40 → **8–12 tokens**, and both speed misses resolve, since the
quadratic concat chain becomes one allocation. If `counting-bits` does not fall
under 3× C++ the cause is elsewhere and I will say so.

### Spelling

At least three candidates per operation, measured on the real Round 30
programs, both tokenizers, reusing existing verbs where a tie allows.

## Part 2 — an honest copy instrument

The `roots == 2` unique-update fallback copy is invisible to
`--explain-copies`: `course-schedule` v1 copies ~5.2 GB with zero copies
reported, and `redundant-connection` runs at **137.5× C++** with **1,188 of
~1,200 samples in `_platform_memmove`** and, again, nothing reported.

**Decision:** every copy site reports site, reason and the retaining root.
Diagnosis only — no ownership behaviour changes this round.

**Forecast:** both programs will report a `roots == 2` update copy whose second
root is a caller or loop-state alias. I expect the instrument to also reveal
copy sites in programs whose earlier copy figures were recorded as clean, which
would make those earlier figures wrong rather than merely incomplete.

## Obligations

No shape recognizers. Earlier profiles keep their meaning. Reference and native
must agree exactly on every new form, at O0 and O2. Fuzz families for empty
strings, empty fields, multi-byte separators, all-separator input and very long
rows. Timing only through `scripts/ab_time.py`.

## What would falsify the plan

If the seven tokenization-blocked problems remain unqualified after 1a, then
tokenization was not the real blocker and Round 30's histogram mis-ranked the
evidence; the honest response is to say so rather than to add more text
features.

## Addendum A — step 0 changes specified behaviour, 2026-10-14

**The Why section's compatibility argument was too strong and is corrected
here.** It said skipping empty fields "cannot change the meaning of any program
that currently runs". That remains true of programs, but it is not the whole
picture: three committed tests **asserted** that empty fields are rejected, and
they had to change.

| Source | Before | After |
|---|---|---|
| `!parsebuf("1,,2",",")` | E016 | `[1,2]` |
| `!parsebuf(",1",",")` | E016 | `[1]` |
| `!parsebuf("1,,",",")` | E016 | `[1]` |

So this is a deliberate narrowing of an exact diagnostic, not merely a widening
of an unreachable path, and it is recorded as such.

Two quota tests also had to be rebuilt. They charged the field count using 8
MiB of newlines, which now yields **zero** fields and therefore no allocation.
They now build genuinely non-empty fields by doubling `"1\n"`, so the quota is
still charged on the field count and E013 still fires.

The reference and native paths were changed together and agree on every form
measured: `"0 \n"`, `"0 \n0 \n"`, `"\n\n"`, all-separator input, and interior
separator runs.
