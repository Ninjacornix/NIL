# ADR 051 — Nested-data ownership, integer-keyed maps and sets

## Status

Preregistered 2026-10-13, before any Round 28 compiler change. Two parts, each
admitted only after its own variant matrix, negative cases, debug/release,
sanitizer, differential, corpus, cohort and depth gates pass. This document
records diagnoses and publishes forecasts; it records no result.

## Why

Research and Round 26 agree on the shape of the gap. Of the sampled NeetCode
suite, **48 graph, 21 grid and 11 keyed-nested** tasks need nested sequences or
integer keys. Round 26 established that nested sequences already exist through
wrapper records but are slower than the integer-link workaround they replace,
and that integer keys must be `!format`-ed into bytes.

## Part 1 — nested-data ownership

### Diagnosis, measured before deciding

`course-schedule` v2 builds adjacency as `v[Row]` with `record Row(to:v)` and
appends to a row's child per edge. Under `--explain-copies` the append reports:

```
kind=concat  reason=live-root-retention  retaining_use=<the row update>
```

So the concat copies because its result is retained by the very update that
replaces the row it was read from. The **static** side is already right: the
emitter selects `@nil_concat_unique` at every adjacency site. It is the
**runtime** test that fails — in-place append requires `a->roots == 1`, and
instrumenting the runtime shows the projected child arriving with
**roots = 4, 3, 2, then 1** across the sites. Only the last appends in place.

A second, larger finding. `course-schedule` **v1**, the integer-link version,
is **193.882× C++** on the largest frozen fixture (100,000 nodes, 199,997
edges; `ab_time.py`, 15 interleaved pairs, 4,433.98 ms against 22.87 ms).
`--explain-copies` reports **zero copies** for it, yet a sampling profile
attributes **1,916 of 1,956 samples — 98% — to `_platform_memmove`** reached
from two sites in `nil_entry`.

Two things follow. First, the copy-hint instrumentation has a **blind spot**:
bulk moves on the replace/slice paths are not labelled as copies, so a program
can be entirely dominated by copying and report none. That is recorded as a
defect in its own right. Second, v1's cliff is the *same* pattern as v2's: its
`Progress(counts,queue,tail)` record is projected, a child updated, and the
record rebuilt — project child, update, put back.

### Decision

Make updating or appending to a child of a **uniquely owned** container happen
in place, by transferring the child edge: take the child out of the parent,
update it as the unique owner, put it back. No shape recognizer — the proof is
ownership, not syntax, and anything unproved keeps copying.

The variant matrix must include rows of rows, map values, record children, and
aliases that **must still copy**: a parent that is still live, a child reachable
from two parents, a returned alias, and a child captured by a loop state that
outlives the update.

### Forecast

| Measure | Forecast |
|---|---|
| v2 copy volume on the largest fixture | falls to near zero |
| v2 versus v1 | v2 reaches v1 or better, closing the nested penalty |
| v1 and v2 versus C++ | **20–60× improvement if copying is removed**, so roughly **3–10× C++** |
| acceptance bar of 3× C++ | **plausible but not assured.** 98% of time in memmove bounds the gain at about 50×, which from 193.9× lands near 4×. Reaching 3× may need a second cause removed |
| application controls | no regression beyond 5% |
| correctness | all seven fixtures, reference, O0 and O2 |

Stating this plainly: the acceptance bar may be missed on the last factor of
two, and the honest outcome would then be a published limit rather than a
claim.

## Part 2 — integer-keyed maps and sets

### Spelling by measurement

Candidates scored with tiktoken 0.12.0 on the `contains-duplicate` kernel,
which is the smallest real program that needs them. cl100k and o200k agreed
exactly on every candidate, so one column is shown.

| Candidate | kernel tokens | vs today |
|---|---:|---:|
| today: bytes keys via `!format` | 51 | — |
| **set, `!set()` with `!add`** | **45** | **−11.8%** |
| set spelled `!set[i]()` | 47 | −7.8% |
| integer map, `!intmap()` | 48 | −5.9% |
| integer map spelled `!map[i]()` | 49 | −3.9% |

The dedicated set wins because membership stores no value, and `!format`
disappears from the inner loop. Signature spelling follows the existing
single-letter convention of `m`, `t`, `v`, `s`.

### Decision

Add i64-keyed maps and a set type with insert, membership, removal, size and
iteration in deterministic insertion order, matching the existing byte-keyed
contract. A fast integer hash; no `!format` on the key path. Keys cover the
full i64 range, including `i64min`, `i64max` and negatives.

### Forecast

| Measure | Forecast |
|---|---|
| `contains-duplicate` kernel tokens | 51 → 45, −11.8% |
| two further hashing or graph problems | 5–15% fewer tokens each |
| map and set controls versus C++ `unordered_map`/`unordered_set` | 1.5–4× |
| newly qualifying problems | 0–3 |

## Obligations

Earlier profiles unchanged. Reference and native agree exactly. Fuzz families
for both parts: aliasing, nested updates, key edge cases at `i64min`, `i64max`
and negatives, iteration order, and removal. A regression test per bug at O0
and O2. Timing only through `scripts/ab_time.py` on an otherwise idle machine.
Gates via `scripts/gates.sh full`, with tests not decreasing.

## Addendum A — the copy quantified, and why it is interprocedural, 2026-10-13

Appended before the code it governs. Earlier text is unchanged.

Instrumenting `nil_set_unique_impl` on `course-schedule` v1 at 20,000 nodes
gives a single, exact answer:

```
32584 SET_COPY roots=2 len=20000
```

Every one of **32,584** element updates copies a **20,000-element** buffer,
and every one copies for the same reason: the buffer arrives with **exactly two
roots** where in-place needs one. That is about **5.2 GB** moved, which matches
the sampling profile's 98% in `memmove` and is reported as **zero** by
`--explain-copies`.

The emitter is not at fault: v1's IR already selects `@nil_set_unique`,
`@nil_set_unique_observed` or `@nil_set_unique_capture` at nine of ten sites.
The static proof holds; the runtime count defeats it.

### Where the second root comes from

A record's root slot roots each of its dynamic fields, so a rooted
`Progress(counts,queue,tail)` holds a root on `counts`. Projecting `b.counts`
produces a value that takes its own root. Two roots, same buffer.

### Why a local fix is unsound

In `(Adj,Progress,i):Progress = Progress(b.counts[c:…], …)` the record `b` is a
**parameter**. The second root belongs to the **caller**, which still holds the
old record for the duration of the call, so the callee cannot release it. Making
the projection borrow instead of root would give one root and an in-place
update — and would mutate a buffer the caller's record still points at. That is
sound only when the caller is about to discard the old record, which is true in
the Kahn loop but is a fact only the caller knows.

So child-edge transfer is **interprocedural**: a record argument at its last use
must hand over its field roots, exactly the territory ADR 049 R3 names. This
revises the forecast above only in difficulty, not direction — the 20–60×
headroom and the 3× doubt both stand, and the work is the transfer, not the
allocator.

### A defect to fix independently of either part

`--explain-copies` reports zero copies for a program that spends 98% of its time
copying, because bulk moves on the replace path are not labelled. Any future
copy claim made with that tool is unreliable until this is fixed, including
claims made in earlier rounds.
