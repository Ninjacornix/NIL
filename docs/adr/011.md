# ADR 011 — Structured control-flow regions

## Context

NIL-020 requires control flow without LLM-generated phi nodes. Current HIR has
immutable typed values and a bounded evaluator. The experimental expression
profiles must retain identical semantics and permit token comparisons.

## Decision

Accepted for M2: add bool values, six signed i64 comparisons, lazy conditional
regions and one pre-test loop with an explicitly typed state tuple. A region
contains instructions and yielded value IDs. Branch regions inherit the values
available at the conditional; their locals never escape. Both branches must yield
one value of the same type. The condition must be bool.

Loop initializers evaluate once in the outer scope. Condition, update and finish
regions receive only the loop state as parameters. Update yields the next state
simultaneously, matching the initializer arity and types. Condition yields one
bool; finish yields one result. State names are positional a, b, … independently
of outer names. No hidden access to outer parameters. Nested regions are allowed.

Expression spelling: comparisons `< <= > >= == !=`, `condition?yes:no`, and
`loop(initials;condition;updates;finish)` in expr-v0/v1 and
`@(initials;condition;updates;finish)` in expr-v2. A tokenizer screen on eight
programs found @ saves five tokens across the corpus under both pinned tokenizers.
Each profile has exactly one loop spelling. The loop keyword is reserved in call
position. Bool literals are `true` and `false`. All existing source function
signatures remain i64 in M2; bool supports conditions and loop-carried state.
No implicit int/bool conversions. Surface syntax remains experimental.

Retain checked arithmetic and bounded execution. The interpreter uses an explicit
work stack for regions and calls; region nesting does not consume function-call
budget. Each executed instruction and region/function yield consumes fuel,
including empty loop regions, so every infinite loop is bounded. HIR region
nesting is limited to 32 independently of the parser limit.

## Alternatives

Explicit CFG/block arguments simplify later optimization but burden initial
source generation. Mutable locals simplify familiar loops but obscure joins and
state types. Tail recursion alone cannot provide the required looping construct.
MIR CFG lowering and optimizations remain postponed.

## Consequences

HIR gains recursive region structure and independent validation. Loops can carry
multiple i64/bool values without a general aggregate type. Reordering arithmetic
or eagerly evaluating branches would violate trap semantics. Fixed i64 function
signatures are a documented M2 restriction, not the final type-system design.
Benchmark compact spellings empirically; do not promise runtime speed from syntax.

## Status

Accepted for M2 implementation; surface syntax is experimental.
