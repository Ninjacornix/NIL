# ADR 050 — Sum and recursive types, pattern matching, Option, nested containers

## Status

Preregistered 2026-10-11, before any Round 26 compiler change. Each step is
admitted only after its own variant matrix, negative cases, debug/release,
sanitizer, differential, corpus, cohort and depth gates pass. This document
specifies a design and publishes forecasts; it records no measured result.
Stop at a completed step if a later step cannot discharge its obligations.

## Context and measured evidence

Main `7af71c6` (Round 25 R2 merged), benchmarks `098f8f4`. Natural qualification
21/150, tuned 23/150. The maintainer pivot is explicit: previous rounds improved
runtime while the stated objective — total tokens to a correct program — stayed
worse than Python, and eleven of the last thirteen ADRs were memory and
optimization work with no new language capability since 2026-10-05.

The blocking fact is representational. NIL has no sum, recursive or nested
container type, so trees, lists and adjacency are encoded as integer links in
flat buffers and structure becomes offset arithmetic (`a[3+3*k]`,
`a[2+2*e]`). Measured on the frozen kernel cut of `balanced-binary-tree`
(cl100k, tiktoken 0.12.0):

| Source | cl100k | vs Python |
|---|---:|---:|
| NIL v1 (index links, explicit stack, memo buffer) | 292 | **+78.0%** |
| Python kernel | 164 | — |
| C++ kernel | 203 | +23.8% |
| NIL v2 draft (sum + recursive + match, this ADR) | **107** | **−34.8%** |

So the token deficit on algorithmic code is the workaround, not the surface
syntax. ADR 024 already concluded that surface compression was not justified by
attribution evidence; this ADR asserts the remaining cost is the missing type
system, and the number above is the preregistered basis for that claim.

Seven of 36 sampled NeetCode problems are validation-blocked and 114 are
unattempted. Eleven of 79 application tasks have no verified solution. Those
counts, not runtime, are what bound general-purpose use.

## Decision

All additions are opt-in expr-v5 surface plus semantic HIR. Earlier profiles and
the default profile are unchanged. No shape recognizer, benchmark name or source
spelling is an admission criterion anywhere.

### 1. Sum types

`sum Name(Variant(type,...),Nullary,...)` declared in the declaration group
before functions, alongside `record`. Names and variant names start with an
uppercase ASCII letter. Payloads are **positional and unnamed**; a variant has
0..64 payload slots. Values are immutable: there is no variant mutation, only
construction and matching. `Name` is a signature type exactly like a record
name. Construction is `Variant(args)` for a payload variant and bare `Variant`
for a nullary one. Variant names are unique across the whole declaration group,
so a constructor needs no qualification; a duplicate is a Check error.

Limits: sums share the 128-declaration budget with records; 1..64 variants per
sum; 0..64 payload slots per variant.

### 2. Recursive types

Declarations are parsed as one group and validated together, so a `sum` may
reference itself, and sums may reference each other in any order. **Records stay
acyclic and earlier-only**: they are inline SSA aggregates with no indirection,
so recursion through a record is rejected as it is today. Recursion is expressed
by a sum payload, which is a pointer. A record field may hold a sum, which is
how a recursive structure reaches into a product.

Values are acyclic by construction: every value is immutable and built
bottom-up, so no cycle can be formed. Reference counting is therefore complete
and no tracing collector is needed for sum nodes.

### 3. Representation and memory

A sum value occupies one opaque slot. Two encodings, discriminated by the low
bit:

- **Nullary variants are unboxed**: the slot holds `(tag << 3) | 1`. Heap nodes
  are 8-aligned so the low bit is otherwise always zero. `None`, `Leaf` and
  `Nil` therefore never allocate.
- **Payload variants are heap nodes**: `{ i64 refs; i64 tag; slot payload[k]; }`.

Nodes are reference counted, not arena-collected: a 10^6-node list must not pay
O(n) per root store, which the existing record child-root traversal would. The
counting discipline is one owned reference per live SSA value:

- construction yields `refs = 1` owned by its result;
- binding a payload slot in a match arm retains it;
- placing a value into a constructed node retains it;
- call arguments are **borrowed** — the callee does not retain, and the caller's
  reference provably outlives the call;
- the returned value's reference transfers to the caller; every other live
  node-typed value is released at its last use.

Release is **non-recursive**: reaching zero pushes children onto an explicit
heap worklist rather than recursing, so dropping a 10^6-node list cannot
overflow the stack. This is a hard requirement, not an optimization.

**Reuse (Perceus).** At a construction site whose input node is observed at
`refs == 1` with the same variant and arity, the node's storage is reused in
place instead of allocated. Uniqueness is a runtime observation at the
construction, never asserted from liveness alone, exactly as `nil_set_unique`
does for sequences. Round 25's ownership and last-use analysis supplies the
static side; any value with another live owner allocates. Old versions of a
value are never observed to change.

### 4. Pattern matching

`?scrutinee(Variant(b1,b2):expr, Nullary:expr)` is an expression. It selects by
variant, binds payload slots **positionally** to fresh local names, and `_`
binds nothing. Arms are **lazy**: only the selected arm's effects, traps,
allocations and calls execute, matching existing ternary and lazy-region
semantics. Arm bodies all have the matched result type. The scrutinee evaluates
once, before any arm.

Two new Check diagnostics, with exact spans, reported before execution:

- **E025** non-exhaustive match — names the uncovered variants; span is the
  match expression.
- **E026** unreachable arm — a variant already covered, or one not belonging to
  the scrutinee's sum; span is the offending arm.

There is no wildcard arm, no nested pattern, no guard and no binding of the
whole scrutinee in this round. Exhaustiveness is therefore decidable by variant
set membership alone, which is what makes E025 exact rather than approximate.

### 5. Option

A single built-in parameterized sum `Option(T)` with variants `Some(T)` and
`None`, **monomorphized at each use site**. This is the smallest sound mechanism
that lets an intrinsic return "maybe absent" without a sentinel; users cannot
declare generic sums in this round. `T` is bounded to i64, u64, u128, f64, bool,
Bytes, Buffer, a declared record or a declared sum.

Bare `None` is admitted only where an expected type is known — a signature
result, a record or variant field, or a match arm — and is otherwise E007. It
carries no payload so it allocates nothing.

Option replaces sentinels in new non-trapping forms rather than changing any
existing signature: `!get` keeps its E019 contract and its callers keep working.

### 6. Nested containers

Element and value positions accept dynamic types: `v[v]` and `v[s]`
(sequence of sequences), `v[Name]` extended to sums, and map values holding
sequences, dynamic-leaf records or sums. Child ownership uses the existing
record-buffer child machinery for sequence children and reference counting for
sum children. ADR 030's deferral of sequence-bearing record map values and
record-buffer rows is lifted only for the cases a gate covers; anything
uncovered stays conservative and is a negative test, not a silent emulation.

### 7. Record-buffer invalid size (B4)

`!buffer[Name](length,fill)` with an invalid or negative length reports
**E014**, like flat `!buffer`. The implementation already does this; EXPR_V5's
record-buffer section still documents E013, which is wrong. B4 corrects the
document and pins the behaviour with an O0/O2 regression test. No code change is
expected; if one proves necessary, E014 is the target.

## Soundness obligations

1. **Immutability.** No operation mutates a reachable value. Node reuse requires
   a runtime `refs == 1` observation at the construction point; every other
   owner forces allocation. Old versions never change.
2. **Counting completeness.** Every live reference is counted. Borrowed call
   arguments require the caller's reference to outlive the call. Leaks and
   double frees are sanitizer-visible and block admission.
3. **Non-recursive drop.** Release uses an explicit worklist. A 10^6-node list
   drop is a required test, not a forecast.
4. **Laziness.** Unselected arms execute nothing — no effect, trap, allocation
   or call. The scrutinee evaluates exactly once.
5. **Exhaustiveness.** E025/E026 are static and exact, derived from variant set
   membership. No runtime match failure exists, so there is no new trap.
6. **Diagnostics and order.** Existing codes, spans and evaluation order are
   unchanged. New syntax must not alter any existing program: the frozen corpus
   is the proof.
7. **Resources.** Node allocation failure is an ordinary resource failure under
   ADR 046/047 and reports E013. Reference counting introduces no deterministic
   quota.
8. **Interaction with Round 25.** Ownership summaries treat a sum-typed value as
   dynamic. Transfer and replay admission must either model sum nodes or refuse
   them; refusing is acceptable and must be stated, never assumed.

## Alternatives

Generic user-declared sums: rejected this round as larger than needed; built-in
monomorphized `Option` is the smallest mechanism that removes sentinels.
Tracing collection for nodes: rejected because values are acyclic by
construction, so counting is complete and cheaper. Arena-allocated nodes with
the existing child-root traversal: rejected because rooting a list head would be
O(n). Wildcard and nested patterns: deferred so exhaustiveness stays exactly
decidable. Mutable variants: rejected; immutability is load-bearing for the
alias and reuse proofs. Keeping records recursive-capable: rejected; inline
aggregates cannot express unbounded depth without indirection.

## Addendum — representation and ownership corrections, 2026-10-11

Appended after the B1 frontend, native lowering and B4 landed, and before the
code it governs. Earlier text is unchanged.

Four corrections, raised by overseer review against the sections above.

### A1. Non-recursive sums and `Option` of a scalar are inline, not boxed

§"Representation and memory" boxes every payload variant. That is wrong for the
common case: `Some(x)` in a lookup loop would call the allocator once per
iteration, which makes a sentinel-free API slower than the sentinel it
replaces, and would defeat the point of item 3 of the original decision.

A sum is therefore laid out by whether it is **recursive**, computed over the
declaration group:

* **Non-recursive sum** — no variant payload reaches the sum itself, directly
  or through another sum or record. Represented **inline** as a tag plus the
  widest variant payload, exactly like a record. No allocation, no node, no
  reclamation. `Option` of a scalar, `sum B(Free,Bound(i))` and every
  enumeration fall here.
* **Recursive sum** — reachable from its own payload. Only its *payload*
  variants are boxed as heap nodes; nullary variants stay unboxed as
  `(tag<<3)|1` as already specified. This is Swift's `indirect` and the usual
  Rust practice, decided by the compiler rather than by an annotation.

Recursion is a property of the declaration group, so the choice is static and
needs no new syntax. Inline sums keep `Type::Sum` at a flattened slot count
like records; boxed sums keep one opaque slot.

### A2. Sum nodes must be reclaimed before B1 is complete

The published limit introduced with native lowering — nodes accumulate until
E013 — is not acceptable as a resting state. B1 is **not** complete until boxed
nodes are reference counted with a **non-recursive** drop, as §3 of the
original decision already requires. Teardown being iterative at process exit
does not discharge that obligation; it only bounds the damage.

Reclamation lands with the counting discipline already specified: one owned
reference per live SSA value, retain on binding and on placement into a node,
release at scope exit through a per-frame slot array so branches and loops are
handled uniformly, and an intrusive worklist through the nodes being destroyed
so a 10⁶-node drop allocates nothing and recurses not at all.

### A3. Call arguments are owned at a last use, not unconditionally borrowed

§"Representation and memory" makes every call argument borrowed. That is sound
but it blocks the reuse this ADR promises: in consume-and-rebuild recursion —
`insert(t,x)`, a map over a tree — the argument is the only owner, yet a
borrowed parameter can never be observed unique, so the callee always
allocates and Perceus reuse never fires where it matters most.

Corrected rule: a sum-typed argument at its **last use** in the caller is
passed **owned**, transferring the reference; every other argument stays
borrowed. Ownership per parameter is inferred with the Round 25 machinery in
`crates/nil-hir/src/parameters.rs` (`Ownership::analyze`, `owns[f][k]`,
`origins[f]`, a least fixed point over the call graph), extended to sum-typed
parameters. Where that analysis is imprecise — notably the two known holes,
every intrinsic being `Unknown` and a region result naming an enclosing local
being `Unknown` — the parameter stays borrowed. Borrowed is always the safe
answer, so imprecision costs reuse, never correctness.

Unique-node reuse remains a **runtime** `refs == 1` observation at the
construction site. Ownership inference only decides whether a caller hands over
its reference; it never asserts uniqueness on its own.

### A4. Order

B3 (nested containers) precedes B2 (`Option`), because B3 unblocks more
problems and A1 already supplies sentinel-free `Option` as an ordinary
non-recursive sum with no allocation and no generics.

### A5. Additional required measurements

* Tree insert/rebuild at O2 versus C++, measured **with and without** node
  reuse, so the reuse effect is isolated rather than asserted.
* An `Option` lookup loop at O2 versus C++, to show that A1 removes the
  per-iteration allocation.
* The 10⁶-node drop measured as a drop, not only as process teardown.

## Addendum B — nested containers, measured refusal of the `v[v]` spelling, 2026-10-11

Appended before the code it governs. Earlier text is unchanged.

### B1. Sequences of sequences already exist

§"Nested containers" of the original decision treats `v[v]` as new capability.
It is not. A wrapper record already supplies it, and has since ADR 030:

```nil
record Row(to:v)
(v[Row],i)=#a[b].to
```

Construction, indexing and nested length all work today. Measured on
`course-schedule`'s adjacency build (cl100k): v1's three parallel integer-link
buffers cost **88**, the wrapper record that already works costs **74**, and a
hypothetical `v[v]` spelling costs **64**. So the spelling would save **10
tokens over what exists**, and the other 14 were available all along.

### B2. The spelling is refused, because nesting is measurably slower

`course-schedule` was rewritten with wrapper-record adjacency and matches v1 on
all seven frozen fixtures. It is **17 tokens shorter (−4.6%) and 3.75× slower**:

| `course-schedule`, largest fixture, O2, 15 reps | median | vs C++ |
|---|---:|---:|
| v1, integer links | 4,448.40 ms | 197.288× |
| v2, wrapper-record nesting | 16,680.95 ms | **739.807×** |
| C++ | 22.55 ms | — |

The cause is already published: appending to a sequence held in a field of a
**still-live record-buffer row** remains quadratic (ADR 030 performance debts).
Integer links prepend in O(1); a nested child is copied per append. A scaling
check at fixed node count confirms the superlinearity — doubling edges costs
v1 ×1.71 and v2 ×2.19.

A `v[v]` spelling would inherit exactly this, so adding it would buy 10 tokens
and import a 3.75× regression. **It is refused on measurement**, consistent
with ADR 026's rejection of convenience additions that are not fundamental.
The useful work here is not a type: it is proving in-place append for a child
inside a live row, which is a compiler optimization against a published debt.

### B3. What remains genuinely new

Map values holding sequences, dynamic-leaf records or sums are still rejected
(`E023`, "record map values must have only scalar or fixed-array leaves"), and
that is real missing capability rather than missing sugar. It stays deferred
here rather than being half-built, because the same append debt would govern
its performance and would make a new feature arrive already slower than the
workaround it replaces.

## Addendum C — arena collection is spaced in entries, not only bytes, 2026-10-12

Appended before the code it governs. Earlier text is unchanged.

Addendum B attributed `course-schedule` v2's 3.75× regression to the
copy-on-append of a child inside a live record-buffer row, and hypothesised a
contribution from `nil_child_roots` traversing every row on each root
transition. Instrumentation **refuted** the hypothesis and found a different
cause.

Counting traversals and sweeps on the nested adjacency build at 20,000 nodes:

| | child rows visited | collections | allocations swept |
|---|---:|---:|---:|
| v1, integer links | 0 | 32,596 | 273,296 |
| v2, nested | 160,000 | 9,272 | **116,586,967** |

So child rooting is negligible — eight calls in total — and the cost is the
**arena sweep**. `nil_collect` walks the whole allocation list, and a nested
collection holds one allocation per row, so each sweep is O(rows). v1 collects
*more often* and stays cheap because its list is short; v2 collects less often
and pays 12,500 visits each time.

### Decision

Opportunistic collection is gated on the entry count as well as the byte
budget. Sweeping costs one visit per live allocation and yields bytes, so the
two must be compared:

* Memory pressure always collects, unchanged, so `E013` behaviour is preserved.
* Below 1,024 live allocations a full sweep is cheap, so byte pressure alone
  still collects eagerly. This keeps byte-churning transforms' locality.
* At or above that, sweeps are additionally spaced geometrically in the entry
  count (`count >= 2 × count_after_last_sweep + 64`), which makes total sweep
  work linear in allocations instead of quadratic.

Collection timing is already documented as implementation-defined in
`EXPR_V5.md`, so no contract changes. No bounds, alias, quota or effect check
is weakened.

### Measured effect

`course-schedule` v2 on the largest frozen fixture, O2, 15 repetitions:
**16,791.43 → 6,427.97 ms**, so 759.331× → **290.681× C++**, a 2.61×
improvement. v1 is unchanged at 205.3×, because its allocation list is short
enough that the new gate never binds.

Application controls, interleaved 25 repetitions to cancel drift, show no
material change: 16 MiB scan +0.6%, 16 MiB transform +1.8%, 1 MiB append
−2.2%. An earlier non-interleaved measurement of a first version of this gate
reported transform +20.4%; that version lacked the small-list exemption, and
the +20.4% was partly a measurement artifact. Both faults are fixed above.

The nested spelling is still **not** admitted: v2 remains 1.42× slower than the
integer-link v1 and the copy-on-append identified in addendum B is untouched.
This removes one of two causes.

### C1. The improvement is measured, not test-pinned

Noted for honesty. The 2.51–2.61× improvement is reproducible on
`course-schedule` v2 against a clean build of the preceding commit, with
matching outputs, but it **could not be reduced to a synthetic case**: two
minimal nested row-append loops show only 1.00–1.51×, i.e. noise. The trigger
is therefore more specific than "nested collection with row appends" and is not
fully characterised.

Collection timing is implementation defined in `EXPR_V5.md`, so it is not
observable through program results and cannot be asserted by a semantic test.
The regression tests added alongside pin what a collection change can actually
get wrong — that results do not change, and that the allocation guard still
reports E013 — and the performance claim rests on the cohort measurement.
